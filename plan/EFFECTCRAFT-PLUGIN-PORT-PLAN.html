Part A — The business view#

1. Executive summary#

CraftBridge lets an iOS or Android developer put EffectCraft's motion-graphics engine inside their own app. A Swift package and a Kotlin library expose everything the EffectCraft command line can do as device APIs: open and save projects, run any of the engine's 763 commands, inspect and edit properties, preview, render frames and export video. The developer brings the interface; CraftBridge brings the engine (PD8).

It works on four ideas:

  1. The same engine, not a port. CraftBridge compiles EffectCraft's own engine for phones, at an official revision and never modified; whatever a phone needs done differently is adapted inside CraftBridge, on EffectCraft's public interfaces (PD4, PD5). On the CPU, a frame rendered on an iPhone, an Android phone and the desktop app is byte-for-byte the same (evidence/03-device-feasibility.md Finding 4).
  2. Native on each platform. The engine's GPU compositor draws through Metal on iOS and Vulkan on Android, and video footage decodes on the phone's hardware decoder where it has one (PD12, PD18).
  3. Generated from EffectCraft itself. The Swift and Kotlin APIs are generated from the engine's own command list. Taking a new EffectCraft release is one script: move the pin, regenerate, compare the API, name the adaptations whose EffectCraft code changed, run the conformance suite (PD4).
  4. A universal core. The parts every Craft app needs on a phone (the request channel, progress and cancellation, the GPU device, folders, fonts, hardware decoding) live in a core that knows nothing about EffectCraft. A future FilmCraft plugin imports the same core (PD9, PD10).

Commercial position. An independent SDK by ChristopherLinnett, "based on EffectCraft by the ArtCraft team", licensed MIT OR Apache-2.0 like EffectCraft, in a repository that is private until hosted CI starts and public from then on (PD2, PD3, PD16). There is no price.

Footprint. One new repository (ChristopherLinnett/craftbridge, one folder per platform) and the Swift distribution repository each release writes (ChristopherLinnett/SwiftEffects). EffectCraft is not touched: the seven places where a phone needs something done differently are CraftBridge adaptations, each listed with the EffectCraft code it relies on, so an update shows which ones to recheck (§15, PD5).

2. The problem and the opportunity#

Today, EffectCraft runs on desktops and in the browser. A developer who wants motion graphics inside a phone app has no way to use it: the engine ships only inside the desktop app, its command-line program and its web build. They choose between a cloud render service (latency, cost, the user's media leaves the phone), a much smaller mobile animation library (no compositing, effects or exports of this depth) or nothing.

What makes it cheap now. EffectCraft's design already separates the engine from its interface. Every action is a command with an id, which the desktop interface, the command line, the control channel and the agent (MCP) server all call the same way (evidence/01-system-inventory.md Findings 8 and 10). The engine builds for phones as it is: its command-line program ran its full document workflow on an iPhone simulator and an Android emulator, with the GPU compositor on Metal and Vulkan (evidence/03-device-feasibility.md Findings 1–7).

Demand. EffectCraft's own tracker asks for mobile support (storytold/effectcraft#1410, open), and two contributors are porting the desktop editor itself to iOS and Android (#1401, #2361). CraftBridge does something different: it offers the engine to other apps, without the desktop editor. There is no usage data for mobile EffectCraft yet; the first measures come from the conformance suite and the sample apps (§9).

3. Customer narrative (PR/FAQ)#

CraftBridge brings EffectCraft's motion-graphics engine to iOS and Android apps. Postcard Studio, a small greeting-card app, now lets its users turn a photo and a name into a polished six-second animated card without leaving the app or uploading anything. "I designed the card in EffectCraft on my Mac, dropped the template into my app, and CraftBridge renders it on the phone: same output as the desktop, previewed live in my own view, exported as an MP4 the user can share," says Leo, Postcard Studio's developer. CraftBridge is a Swift package and a Kotlin library; every command EffectCraft's command line offers is a method call.

Question Answer
What can my app do with it? Everything the EffectCraft command line does: create and edit projects, run any engine command, read and set properties and expressions, render frames, export H.264, HEVC, AV1, ProRes, WebM, GIF, image sequences and audio, render templates, replay repro scripts, talk to on-device agents over MCP and measure render times (§4, PD6).
Does it include an editor interface? No. It renders into your view or gives you images; you build the interface (PD8).
Does it use the GPU? Yes: Metal on iOS, Vulkan on Android. Devices without a suitable GPU render on the CPU, whose output is the reference the GPU path matches (PD11, §17).
Is the output the same as the desktop app? Rendered frames are identical to the desktop's. Encoded video files are equivalent but not byte-identical, because the encoder splits frames by the device's core count (evidence/03-device-feasibility.md Finding 5).
Which devices? iOS 17 and later; Android 10 and later on 64-bit ARM with FP16 (Cortex-A55 and A75 and newer), plus x86_64 emulators (PD11).
What does an older Android phone do? An Android arm64 phone whose processor lacks FP16 (Cortex-A53, A57, A72 and A73, as in a Snapdragon 625 or 665) is refused when your app starts its engine: the start answers Unsupported in a sentence that names the missing feature, before any engine code runs, so the app keeps running. Your app tells its user that the app's video engine needs a newer processor than the phone has, and offers what it can do without the engine (PD11, §16, §23).
How big is it? About 60 MB per architecture before store compression; each release reports the exact size (PD15).
Can exports continue when the user leaves the app? Yes, if your app runs them as a background task; CraftBridge provides progress, cancellation and recipes for iOS and Android (PD14).
Can users load effect plug-ins? Expressions always run. EffectCraft's JavaScript scripts are not part of the phone build: an app that wants what a script does runs the same engine calls in succession (PD13). WebAssembly plug-ins load on Android, and on iOS only from your app bundle, and you can switch them off (PD13).
How do updates from EffectCraft arrive? Each EffectCraft release is taken by one script that moves the pin, regenerates the API, names the CraftBridge adaptations whose EffectCraft code changed and runs the conformance suite (PD4).
Is it an ArtCraft product? No. It is an independent SDK based on EffectCraft by the ArtCraft team (PD2).

5. The experience, step by step#

The running example. Leo builds Postcard Studio, an app for animated greeting cards. On his Mac he opens EffectCraft's built-in template "Social Square 1080×1080" (1080 × 1080, 30 fps, 6 s, so 180 frames), adds a Name text control and a Photo media control, and exports it as Birthday Card.ectemplate. In the app, Maya makes a card for Sam on her iPhone 15; her friend does the same on a Pixel 8. CraftBridge has no interface of its own (PD8), so each step below shows what the person does and the call that does it.

  1. Leo adds the SDK. In Xcode he adds the SwiftEffects package and its CraftBridgeEffects product; on Android he adds io.github.christopherlinnett.craftbridge:effects (PD16). He bundles Birthday Card.ectemplate in the app (§22, §23).
  2. The app starts an engine. Postcard Studio creates one engine with its own folders and asks for the GPU. On the iPhone 15 the engine reports Metal; on the Pixel 8, Vulkan (§16, §17).
    let engine = try await EffectsEngine.start(folders: .appDefault, gpu: .preferred)
  3. Maya picks the card. The app opens the template and sets its controls. A photo from the picker is passed as a file path (§19).
    let card = try await engine.templates.open(bundleURL("Birthday Card.ectemplate"))
try await card.set("Name", "Sam")
try await card.set("Photo", media: photoURL)        // sam.jpg
  4. Maya watches the preview. The app's own view shows the card playing. Frames are rendered on the GPU and drawn straight into that view (§17).
    try await engine.preview(card.comp, into: metalLayer, at: .seconds(2.0))
  5. Maya exports. She taps Share. The app exports a 1080 × 1080 H.264 MP4 of all 180 frames and shows a progress bar; she can cancel (§19).
    let job = try await engine.export(card.comp, to: outputURL, format: .h264, progress: { done, total, secondsLeft in … })
  6. Maya leaves the app half-way. Postcard Studio runs the export inside its iOS background task (or Android foreground service), as the CraftBridge recipe shows. The export continues; if the system stops it, the half-written file is removed and the app offers to start again (§25, PD14).
  7. The card is shared from the exported file, which never left the phone.
  8. EffectCraft releases a new version. The SDK's maintainer runs one update script, and Leo gets the new commands as new methods in the next CraftBridge release (§24).

  • Who gets it. The repository is private to ChristopherLinnett until hosted CI starts, then public (PD3). Apps consume the packages from a checkout (ios/sdk/, android/sdk/) or, from the first release, from SwiftEffects and the GitHub Packages feed.

13. Lifecycle and editability#

Three lifecycles matter: the engine inside an app, the GPU an engine draws with, and the upstream pin the SDK is built from. A project document has no lifecycle of its own beyond EffectCraft's: it is a .ecproj file in the app's folders, edited by engine commands exactly as on the desktop.

ID Rule Enforced by
L1 One engine owns one EffectCraft session; every call runs on the engine's own thread, in the order the app made it. craftbridge-core engine actor (§16)
L2 A call that edits the document is recorded in its undo history exactly as on the desktop. Backend::exec → Session::execute (crates/automation/src/backend.rs:69-92)
L3 While an export runs, the engine answers only progress, cancel and info; every other call waits in order until the export ends. engine actor (§16, §19)
L4 Cancelling an export stops it with Session::stop_render; the exporter removes the files it opened for that output and keeps earlier outputs. crates/engine/src/render_queue.rs:103-106, :691-692

14. Data model and contracts#

CraftBridge keeps its native boundary small and generic, in the shape craft-web-api gives every Craft web build (evidence/04-craft-suite-shared-core.md Finding 6): one Engine object with a JSON request call, plus binary calls for frames. The app crate answers a method table; the Swift and Kotlin layers turn it into typed calls.

Every engine call throws CraftError, mcp, frame, suspend_gpu and resume_gpu included: suspend_gpu and resume_gpu are calls like the rest, answered in the order they were made, so a render made before a suspend runs on the GPU and one made after it on the CPU, and a closed engine throws Internal as request does. A suspend made during an export waits for the export to end, as every call but info, progress and cancel does (§16 behaviour 3), since the engine cannot reach the session inside it: the export renders on the device it started on until then. resume_gpu answers None once the app holds a device and the CPU note info.gpu reports when none came, so a caller tells the two apart from the answer; it throws only what the app answers when it cannot take the device, since no device is no failure. mcp(line) answers the reply line, or None for a line that needs no reply (a notification); a closed engine and a caught panic throw Internal, as request does, and never answer as a reply line, since a reply the app never wrote must not read as one. UniFFI's async_runtime takes tokio and nothing else, and these calls need no runtime: the foreign caller polls each async fn on its own executor (UniFFI, Async/Future support), and at its first poll the call is handed to the engine and then awaits the oneshot channel the engine thread answers it on (§16), so the engine runs calls in the order they were made and no thread blocks for an answer. shut_down hands the stop to the engine as it is made, so every call made after it is refused in order, and waits for the engine thread to stop (stopping joins it) on a thread of its own; made from inside one of the engine's own calls, a progress listener's, it answers at once, as the core's close does. recovery is no async call: it answers at once with what the start did about the pending-export journal (§16, D-17), the files and folders it deleted, left, refused to touch and could not delete, as text, so an app can tell its user what a killed export left behind; it throws Io only for a path that is not valid Unicode, which no text can name. The boundary's CraftError, GpuChoice, PixelFormat, FrameBytes and CodecInfo are the core's own types, exported with #[uniffi::remote], not second definitions; Folders is a record of its own because it holds paths as strings, and CancelToken an object that wraps the core's. In both bindings each CraftError variant's text is the field detail, since Kotlin's exception for a variant already has a message of its own (uniffi.toml renames it for both languages). What an error says to the app's user is the core's Display of it (a variant's text, a failed command's name before it and its step after, cancelled), which craft_error_message answers, so the Swift and Kotlin layers read their messages from it and keep no second copy of how each variant reads. One size check covers every answer that grows with what a call asks for; an error's text and resume_gpu's CPU note, which no parameter makes grow, and the recovery report, which the journal's own size bound keeps far below the limit, cross unchecked. UniFFI writes a length into the buffer it lowers as i32::try_from(len).unwrap() (0.32.2, as in 0.28.3 and 0.30.0), so a longer value panics inside UniFFI and the app gets no CraftError, and Kotlin reads a buffer through one ByteBuffer of at most i32::MAX bytes. So a frame whose data is longer than MAX_FRAME_BYTES (i32::MAX less the 16 bytes of the record's other fields; a CPU render reaches it at about 23170 × 23170 RGBA), a request or request_with_progress answer longer than MAX_ANSWER_BYTES (i32::MAX: the text crosses whole) and an mcp reply line longer than MAX_MCP_LINE_BYTES (i32::MAX less the 5 bytes of its tag and length) each throw InvalidParams, the row for parameters the core refuses, naming the length, the limit and what to ask for less of, and the call can be made again for less. The bytes are copied as they cross: UniFFI serialises the record, data with it, into a buffer it hands over, and Kotlin's ByteArray lives on the JVM heap, so no call promises zero-copy.

Platform handles live in craftbridge-core-ffi's platform modules (§20): attach_metal_layer(engine, layer) on iOS; on Android the JNI function NativeSurfaces.acquire(surface) returns an id that attach_window(engine, id) takes. Each app's distribution crate exports one constructor, for EffectCraft start_effects_engine(folders: Folders, gpu: GpuChoice) -> Result<Arc<Engine>, CraftError>.

The rank and uniffi rules are about what ships, so dev-dependencies, which only a crate's own tests compile, are outside them; the tool rule is not, since a tool may reach every app, and a test that took one would reach them through it, nor is the rule that nothing but a tool depends on a combined distribution crate, which links every app it ships. A Craft app's crate is known by its name or by the app's repository it comes from.
  • uniffi appears only in -ffi crates, and only a distribution library builds a staticlib or cdylib, and it builds both; no crate is a Rust dylib (D-4). States.

  • Pinned: rev names an official storytold/effectcraft commit; info reports that commit in full as pin (§21).
  • Update in progress: the update script has moved the pin and named the adaptations whose EffectCraft code changed; the update merges once each named adaptation is rechecked and the gate passes (§24).

Edge cases.

  • An update changes code an adaptation follows (a new render flag, a renamed command an adaptation calls): the script names the adaptation; RenderRequest gains the field and the corpus the scenario, in the same update.
  • An update removes a public item an adaptation uses: the build fails at the gate, and the adaptation is rewritten on what upstream offers instead, in the same update.
  • Upstream adds a public interface that does what an adaptation does (a session with explicit folders, an encoder interface): the adaptation moves onto it and its entry in tools/adaptations.toml is retired (upstream wins, AGENTS §7).

17. GPU and frames design#

The device. craftbridge-core::gpu creates the GPU device itself rather than letting the compositor pick one (AD12, evidence/03-device-feasibility.md Findings 6–8):

  • Backend: wgpu::Backends::METAL on iOS, wgpu::Backends::VULKAN on Android. GL is never requested: the compositor needs compute shaders, which the emulator's GL lacked (evidence/03-device-feasibility.md Finding 7).
  • Limits: wgpu::Limits::default().or_worse_values_from(&adapter.limits()), with max_texture_dimension_2d capped at 16384 and max_buffer_size from the adapter, as the compositor does for those two (crates/gpu/src/context.rs:1430-1435). This is the request that worked on the iOS Simulator's Metal device.
  • Hand-over: the app crate passes (adapter, device, queue) to effectcraft_gpu::Gpu::new (crates/gpu/src/lib.rs:162-166), which is how the desktop app shares its window's device, and sets Session.accel.
  • No device: Session.accel_note records why, info.gpu reports it, and every render runs on the CPU (L7).

Preview into the app's view (zero copy, PD8).

  1. The app attaches its CAMetalLayer (iOS) or Surface (Android) once (§20 platform module); the core keeps a wgpu::Surface configured Bgra8Unorm (iOS) or Rgba8Unorm (Android), non-sRGB, PresentMode::Fifo with one frame in flight (the desktop window's LOW_LATENCY, effectcraft: apps/effectcraft/src/main.rs:475-482), CompositeAlphaMode::PostMultiplied where offered, else Opaque, else Inherit: Android's surfaces offer Inherit alone, because its window manager composites the window (Android's Vulkan loader, frameworks/native/vulkan/libvulkan/swapchain.cpp), so the pass writes alpha 1 there, as for Opaque.
  2. present({comp, time}), the fields of a frame request, asks the app crate for a display frame: Gpu::render_display leaves the composited frame on the GPU as premultiplied Rgba8Unorm with mips (effectcraft: crates/gpu/src/lib.rs:143-147, effectcraft: crates/gpu/src/lib.rs:224-236). The app crate asks for it only while the project is on Mercury GPU Acceleration, as EffectCraft's viewer does (Renderer::active_accel, effectcraft: crates/ui-egui/src/frames.rs:1978-1993); a project on Mercury Software Only previews from the CPU, as its frames render.
  3. The core's blit pass (the WGSL in blit.rs, one full-screen triangle drawn into the aspect-fit viewport, linear filtering on the mip chain) scales it into the surface texture between opaque black bars, un-premultiplying it first when the surface reads straight colour (PostMultiplied off iOS), and presents (AD14). On iOS the layer is configured PostMultiplied, the one non-opaque mode wgpu's Metal backend offers, which only clears the layer's opaque flag; Core Animation reads every non-opaque CAMetalLayer as premultiplied (measured on the simulator: a half-transparent red over blue composes as the blend only when the pass writes the frame as it is held), so there the pass writes the premultiplied frame as it is and never un-premultiplies it.
  4. When render_display returns None (the GPU declined the frame), or the app crate does not ask for it, the app crate renders on the CPU (Session::render_rgba8_alpha, crates/engine/src/session/render.rs:132-143) with the comp's own alpha, as the display frame keeps it, so both show one picture and the comp's background colour neither, and no larger than the device's texture limit; the core uploads it, premultiplied as the blit reads every frame, into a reusable texture before the same blit.

Platform images and PNG (frame).

  • Png: Backend::render_with (crates/automation/src/backend.rs:122-124), the CLI's own path.
  • Rgba8Straight: Session::render_rgba8_alpha as is.
  • Bgra8Premultiplied: the same buffer swizzled and premultiplied by the core, ready for a CVPixelBuffer (kCVPixelFormatType_32BGRA, premultiplied first) on iOS; Android builds a Bitmap (ARGB_8888, premultiplied) from Rgba8Straight with Bitmap.setPixels, which premultiplies each colour as it stores it. Bitmap.setPremultiplied only labels the pixels the bitmap already holds and copyPixelsFromBuffer copies bytes as they are, so neither converts straight bytes: they would show a translucent pixel too bright. On the emulator (Android 14) and on the acceptance phone (Android 17) setPixels stores, for every one of the 65,536 pairs of an 8-bit colour and an 8-bit alpha, the byte the core's own Bgra8Premultiplied rule writes ((value × alpha + 127) / 255), so the core keeps no premultiplied RGBA row for Android (D-10). A HardwareBuffer is that bitmap copied to Bitmap.Config.HARDWARE, whose buffer a bitmap hands out from Android 12 (API 31); before it the call answers Unsupported (§22, §23).

States.

  • GPU attached: Metal or Vulkan, info.gpu = "<adapter> (<backend>)".
  • CPU only: CpuOnly chosen, no adapter, device lost, or (iOS) the app is in the background without the continued-processing GPU entitlement (Metal rejects background command buffers, evidence/05-mobile-platforms.md Finding 19). The core drops the GPU on the first device-lost or uncaptured error, before its next call. On iOS the Swift layer's BackgroundController calls suspendGpu() on UIApplication.didEnterBackgroundNotification unless the app chose BackgroundPolicy.keepGpu, resumeGpu() on UIApplication.willEnterForegroundNotification, and attaches the layer of its PreviewTarget again once the device is back, since the suspend dropped the surface with the device (§22).
  • Surface lost: the layer or surface was resized (outdated): the present that finds it configures the surface again and answers Gpu, and the next draws. Destroyed (lost): every present answers Gpu until the app attaches a new surface, and the session is untouched; a surface already destroyed when the app attaches it answers Gpu at the attach. Any error the device reports while a frame is acquired, drawn or shown answers Gpu too, never wgpu's default panic, and a frame that failed to draw is not shown. After detach_preview it answers Gpu { "no surface" }.

Edge cases. A comp larger than the device's texture limit: the compositor renders on the CPU for that comp (its existing decline path), and its preview frame is fitted to the limit. A preview during an export: waits (L3); the app shows its last frame.

Tests. Desktop: the blit pass against a reference image; CPU and GPU frame outputs equal within the compositor's own GPU tolerance. Simulator and emulator: present into an offscreen layer and surface, read back. Devices: V4, which runs the core's own device tests on each device: the clamped request must be given, on the backend the platform asks for, with no limit above the adapter's, and the compositor's own request, unclamped, is given or refused exactly as the adapter's limits say, its refusal recorded in wgpu's words.

The NDK has no 10-bit YUV image format (AIMAGE_FORMAT_* in r28 NdkImage.h), so a 10-bit picture is read from its image's hardware buffer (AImage_getHardwareBuffer, API 26): the reader is made with AImageReader_newWithUsage and AHARDWAREBUFFER_USAGE_CPU_READ_OFTEN, since the AImageReader_newWithUsage documentation (r28 NdkImageReader.h) pairs every format but AIMAGE_FORMAT_PRIVATE with a CPU read usage and refuses one on AIMAGE_FORMAT_PRIVATE, whose images the CPU cannot read; its format is the HAL YCbCr_P010 format (AHARDWAREBUFFER_FORMAT_YCbCr_P010, 0x36), a value outside the AIMAGE_FORMAT_* list that header documents, which AImageReader accepts from Android 14 (API 34) (isSupportedFormatAndUsage in AOSP frameworks/av/media/ndk/NdkImageReader.cpp names it from android14-release and in no earlier release branch) and refuses before it, so before Android 14 no decoder starts for a 10-bit stream and the software decoder takes it from its first sample. The YUV_420_888 reader is no way round that: it takes a producer's YCbCr_P010 buffer only through Android 11 (isPossiblyYUV, AOSP frameworks/base/media/jni/android_media_Utils.cpp, names YCbCr_P010 from Android 12 on), and through Android 12 AHardwareBuffer_lockPlanes locks such a buffer as one plane (AOSP frameworks/native/libs/nativewindow/AHardwareBuffer.cpp, whose AHardwareBuffer_formatIsYuv names YCbCr_P010, and whose planes give its luma the two-byte pixel stride, from android13-release), so no Android before 14 gives a 10-bit picture through either reader. The buffer is locked with AHardwareBuffer_lockPlanes (API 29) and read only if AHardwareBuffer_describe says it is YCbCr_P010 and its planes are the biplanar layout (16-bit luma; Cb and Cr words interleaved four bytes apart, the Cr plane two bytes after the Cb plane); any other buffer, a vendor-tiled format included, is an error, which Fallback answers by switching to the software decoder, so a vendor-tiled format never reaches CraftBridge. The words become FilmCraft's 10-bit DecodedFrame through the same host-tested conversion VideoToolbox's 10-bit pictures use.
  4. With one, it returns Fallback<VtDecoder> or Fallback<McDecoder>; without one, or when one cannot start, it returns None and FilmCraft's software decoder takes the stream: FilmCraft opens a stream with the first factory that answers, so the factory never answers an error (crates/codecs/src/lib.rs:112-120). That decline path ran in the iOS Simulator, which has no hardware decoder, with a byte-identical result (evidence/03-device-feasibility.md Finding 14).
  5. Frames are converted into the same DecodedFrame layout the software decoder produces for that stream (filmcraft crates/codecs/src/video.rs:19-55), so EffectCraft's pipeline sees no difference.

Encoding. The first release exports through EffectCraft's pure-Rust encoders (PD12). Those encoders are internal to EffectCraft's export crate (effectcraft: crates/export/src/encode.rs:100-115), so hardware encoding (W6, F1) lives in CraftBridge's exporter (AD7). For an H.264 or HEVC job with hardware encoding chosen, it runs the same item through FileExporter (effectcraft: crates/host/src/lib.rs:25-30) as a Targa sequence and a WAV, handed to an in-memory sink and never written to disk: the sink receives each finished file, sequence frames from the render threads (effectcraft: crates/export/src/out.rs:8-10), and Targa frames are uncompressed (effectcraft: crates/project/src/render_queue.rs:528-530). The exporter puts the frames back in order, encodes them with craftbridge-media's VideoToolbox or MediaCodec encoder and the sound with the platform's AAC encoder, and writes the MP4 with the ISO BMFF writer EffectCraft's own export uses, tagged BT.709 limited range as EffectCraft tags its own (effectcraft: crates/export/src/encode.rs:22-58). Every frame is still rendered by EffectCraft's pipeline, so its timing, colour and size rules apply unchanged.

A request chooses hardware encoding with the hardware field of its export (§14), or of the output of a template.render, which is a render request too; it is off unless given, and the choice lasts for that one render, so the project's own queue and every command run through exec encode as EffectCraft does. A request that sets queue and hardware both is refused before anything renders, as InvalidParams naming both fields and saying a queued render encodes through the render queue and its own encoders, because the choice would otherwise be dropped without a word; it is the request's own reader that refuses it, so a template.render's output is refused the same way. The sub-jobs are the item with its own crop, resize and channels: a Targa sequence of the frames (an alpha matte stays one), and a WAV of 16-bit samples in the movie's rate and channels. Each Targa frame is cut or padded to the coded size as EffectCraft's own movies fit theirs, converted with EffectCraft's own BT.709 limited-range conversion (effectcraft: crates/raster/src/yuv.rs:25-50), and encoded in order. The picture track's timescale is the frame rate's numerator and each sample lasts its denominator; the session is asked for no frame reordering, so no sample has a composition offset and the track has no edit, where EffectCraft's own H.264 track carries one for its encoder's delay, and the movie fails on a picture the encoder returns out of its turn, which would otherwise be shown at another picture's time; the key frame interval is EffectCraft's (two seconds for H.264, the module's for HEVC). The AAC track's edit skips the encoder's priming and ends at the sound's own last sample, not at the end of the encoder's last 1,024-sample unit, and its samples sit in a roll sample group of distance -1 (ISO/IEC 14496-12): Apple's readers take the priming from the edit alone only from a track with that group, and from one without it drop the priming twice and play the sound early. EffectCraft's own movies have neither at the pin (docs/upstream-updates.md). The MP4 is written with FilmCraft's revision of the same ISO BMFF writer, since the core carries FilmCraft's and EffectCraft's own copy is a different revision of the same crate. The exporter leaves a job with EffectCraft's exporter, before anything renders, when the hardware path cannot reproduce it: another format, HEVC at Main 10 or at a chosen level, Skip Existing Files, a storage hook with Use Storage Overflow, a render log beyond errors, a rate or channel count the AAC encoder cannot take, or a device whose hardware encoder will not start for the movie (every device where the platform's encoders decline it; the iOS Simulator encodes on its Mac's, and an Android emulator, whose MediaCodec video encoders are all software, runs the export through EffectCraft's encoders). A stopped or failed export removes its movie, as EffectCraft's does.

States.

  • Hardware: info.hardwareDecoding is true, the registration having found a hardware decoder (availability() is Hardware("VideoToolbox") or Hardware("MediaCodec"), the backend FilmCraft's diagnostics name); it is false in every other state, and before any engine has started. info.decoding counts what the hardware decoders have done since the process started (sessions, pictures, declined and fallbacks, which only grow), so an app, or a test on a phone, sees that a decoder failed and the stream went on in software, which its pictures do not show, since the two decoders give the same ones.
  • Declined: no hardware decoder for this stream (the simulator, an emulator with no decoder for the codec, a profile the device lacks, AV1 on a device with no hardware AV1 decoder, 10-bit AV1 on Android, 10-bit H.264 or HEVC on an Android before 14 (API 34) or on one whose decoder gives no YCbCr_P010 buffer), or a stream the hardware decoders here do not take (anything but progressive 4:2:0 at 8 or 10 bits, VP9); the software decoder decodes it.
  • Failed mid-stream: the wrapper switches to software and replays from a restart sample before the oldest picture the caller does not have yet.
  • Off: the app turned hardware decoding off.

Edge cases. A stream whose decoded frames differ between hardware and software would show as a conformance failure (T23); H.264 and HEVC decoding is exact by specification, and EffectCraft's own desktop test of VideoToolbox decoding measured bit-exact output (storytold/effectcraft#819). Emitted code. For layer.newText the Swift is extension EffectsEngine.LayerCommands { public func newText(text: String? = nil, name: String? = nil, position: Vec2? = nil, …, extra: [String: JSONValue] = [:]) async throws -> JSONValue }, which calls request("exec", {"command": "layer.newText", "params": {…}}); Kotlin emits the matching public suspend fun newText(vararg namedOnly: NamedArguments, text: String? = null, …, extra: Map<String, JSONValue>? = null): JSONValue, whose code calls nothing a command, key or namespace of the same name could answer instead: it reaches the engine through this, and extra defaults to the literal null, since a command emptyMap would answer a bare emptyMap(). Every argument is passed by name, the first included, so a key EffectCraft adds, wherever it stands, takes no old call's value. Swift's labels require that. Kotlin has no named-only parameter, so each method takes first a vararg of NamedArguments, a type :core defines with no value: an argument passed by position would fill it and does not compile, and every parameter after a vararg can only be named. The other ways each leave a gap: plain parameters let a positional call hand its value, extra's too, to a key added before it, so that every such key would break apps and need a major version, and a call whose types agree would compile with its values on the wrong keys; a lint runs only where an app runs it; a parameter object or builder for each command parts from the Swift shape; and a first key left positional would move onto a key put before it. Names follow the id (renderQueue.setRender → renderQueue.setRender(…)); a reserved word is escaped, and a name that would start with a digit takes its holder's name in front (view.3d → view.view3d). extra passes keys the rules did not type, and the engine still validates every key (check_params). An enum key is a value type, never a language enum: in Swift a RawRepresentable struct with a static member for each word (renderer: .classic3D), in Kotlin a value class with a companion constant for each, so no switch or when over it is exhaustive and a word EffectCraft adds later breaks no app's build; its initializer or constructor makes the value of any word. Neither facade has a method for a command the surface marks refusedUnderConfinement or withheldByPlugin: the confinement or the plugin's door refuses every call of it, so a method could only fail, and a namespace left with no method of its own or below it has no type and no file (at the pin, file.watchFolder).

Diff. diff <old> <new> reads two surface files through the types the generator writes them with, and lists the commands, keys and tools that were added, removed or changed (required-ness, type, enum values, key order, a tool's input schema), one line each, sorted, then a count; a line that starts with # is a comment. A change is breaking when an app written against the old facade can fail to compile or run once built against the new one, and the doubtful cases break: a removed or renamed command, key, tool or enum word; a key that is new and required or became required; a key of another type, either way; keys the command keeps in another order, since Swift takes arguments only in their declared order; a command or tool an app can call that became refused under confinement, a command an app can call that the plugin came to withhold, or a tool an app can call that became bridgeOnly; or a tool an app can call whose input schema changed other than by a description, a new optional property or an optional property that was required. An entry no app could call — a tool that was bridgeOnly or refused, a command that was refused or withheld — breaks nothing, whatever becomes of it, and its changes are still listed: the engine runs headless (§19), which hides what is bridgeOnly, always confined (AD9), which answers what is refused before it runs, and behind the plugin's door (AD11, AD19, AD20), which answers what it withholds before the engine sees it, and no facade gives such an entry a method (Emitted code), so no app wrote a call to it. A new command, enum word (no Swift switch or Kotlin when over an enum key can be exhaustive: Emitted code) or tool, a new optional key wherever it stands (a Swift call leaves out a defaulted parameter, and every Kotlin call names its arguments: Emitted code), a refusal or a withholding lifted, and a changed label, journal flag, params text or description are compatible. Exit code 0 when nothing breaks, 2 when something does (the report names each, §24), 1 when a file cannot be read or parsed (the message names it) or the report cannot be written; a command line that is no command exits 1 too, so that 2 means a breaking change and nothing else.

24. Upstream update loop design#

tools/update-upstream.sh <upstream-commit> takes a new official EffectCraft revision in one run (PD4, PD17, L9). It need not be automatic, only quick to take: it does the mechanical steps and names what a person must recheck. UP-9 builds steps 1 and 2 and uses them to set the first pin, so the generated tables are never written by hand even once; OPS-4 adds steps 3 to 7. Any GitHub call it makes names the ChristopherLinnett account (GH_TOKEN=$(gh auth token --user ChristopherLinnett)), never the machine's active login.

  1. Fetch storytold/effectcraft and read the new revision's Cargo.toml and Cargo.lock.
  2. Pins: write the new rev and EffectCraft's FilmCraft revision into [workspace.dependencies] of rust/Cargo.toml, and move each Craft library pin there to the revision the new EffectCraft's own manifest pins that package at, stopping, naming it, at one that manifest names with no Craft library revision, and leaving one it does not name; regenerate [patch.crates-io], [profile.dev] and [profile.release] from upstream; start Cargo.lock from upstream's and resolve CraftBridge's own crates whenever a pin, a Craft library pin among them, or a [patch] table moves, which changes what resolves, and keep the lock when only a profile or a table's layout changed, which Cargo's resolution does not read (D-21).
  3. Adaptations: for each live entry of tools/adaptations.toml, diff the EffectCraft files and items it lists between the old and the new revision, and name every adaptation whose items changed, with its diff, for a person to recheck against upstream's new code (§15); the run's report lists the list's retired entries apart from the live ones, each with the commit that replaced it.
  4. Regenerate: cargo xtask generate (the API surface and both facades); craftbridge-effects-codegen diff against the previous surface.
  5. Gate: tools/ci.sh rules duplicates conformance rust_mobile, the stages that read what an update changes, never the whole gate, which is hosted CI's (AGENTS §12): desktop conformance against the new revision's CLI, the mobile type-checks, and rules, which holds the duplicate-crate check and the pin's own rules over the new lock, beside duplicates, which every local change runs.
  6. Record: append to docs/upstream-updates.md: from and to revisions, the adaptations named and how each was resolved, commands added, changed and removed, the gate result.
  7. Versions: name every version in android/sdk/gradle/libs.versions.toml and the Gradle wrapper that has a newer release, for a person to take, each in a change of its own. This is where library versions are checked: the gate's Lint leaves GradleDependency and AndroidGradlePluginVersion off, because a release elsewhere is no fault of the change it gates (AGENTS §10).

States. Up to date · updated cleanly (commit ready) · adaptations to recheck (the run completes and lists them; the update merges once each is rechecked) · breaking API change (exit 2; the next release is a major version) · gate failure (stops with the failing scenarios).

Edge cases. Upstream adds a public interface that does what an adaptation does: the adaptation moves onto it in that update (§15). Upstream adds a CLI flag or method: AD3 lists the CLI's flag code, so the script names it, and the corpus gains a scenario. A FilmCraft revision change: taken from EffectCraft's Cargo.toml; the duplicate-crate check proves one copy of filmcraft-codecs (D-13). Upstream adds a tool that takes no argument and whose descriptor does not say it only reads: regeneration stops before the tool runs, naming it (§21), for a person to read the tool and recheck how the surface asks it. Upstream adds a tool that takes no argument and whose descriptor says it only reads: regeneration runs it on the empty session, since the word promises no change and not that it reads nothing of the machine, and the adaptations step names the surface's reading of the tools for a person to read it.

Tests. A dry run against the current pin produces no changes and says that nothing changed, and one on a tree whose [patch] table was edited by hand writes the table back and names it; a fixture surface with a removed command makes diff exit 2; a fixture revision that changes a file an adaptation lists names that adaptation; a Craft library pin follows the revision upstream's manifest pins its package at, one upstream names with no such revision stops the update by name, and a moved one starts the lock again from upstream's; the gate step runs the stages it names and fewer than the whole gate; a fixture list's retired entry is shown apart, rechecked by nothing; a catalog version behind its latest release is named.

29. Non-functional requirements#

  • Privacy. No network calls and no telemetry; the engine reads only the app's container, its bundle and paths the app passes, and writes only its container (L5). Nothing is logged off the device.
  • Security. Hand-written unsafe only in the platform modules, each block justified (§20); WebAssembly plug-ins run in EffectCraft's interpreter sandbox and load only where the app allows (PD13); no helper processes (AD1), and the engine's two model downloads — the commands that fetch weights by starting the system's curl — are answered Unsupported on every path, so no process starts at all (AD11).
  • Reliability. EffectCraft's "never crash" rules hold in every CraftBridge crate; a panic becomes Internal and the document stays (§16). A cancel takes effect within one 100 ms poll plus the frame being rendered.
  • Responsiveness. No engine call blocks the caller's thread; all are async (§20).
  • Performance. First-preview and export times and peak memory of the running example on each acceptance device are recorded as the baseline (V5), in conformance/effects/baseline.toml, the one place that holds the figures, how they are measured and the line the measurements print, and are reported per release; a release slower than the baseline by more than 10 % is flagged. A release's own figures are measured by the owner before G2, on both phones with the same measuring tests, and the line each run prints is added by cargo xtask release-figures add to one file of the repository's ignored release/figures/ folder, under the commit measured (a measurement needs ten fresh installs on each phone, one of them reachable only wirelessly and the other behind the machine's lock, which no release run can hold for every release); the release script reads that file through cargo xtask release-figures judge, which applies the file's own [comparison] rule, so the notes quote the verdict and no script holds the rule or the file's format. The conditions are written once in the same file, as the figures that carry a condition (the cap the record's own runs read, condition = "record", or a bound the file states once, condition = "at_most": no serious thermal state, a battery at or under 33.0 C) and each reader reads them, so a run made on a throttled phone is counted, named in the notes and left out of every comparison, and a release with fewer than ten runs in the record's conditions is reported and never judged. A release with no file, one measured at another commit, or one whose file holds no run says in both notes that it was not measured. On the Xiaomi the three preview figures are reported and never flagged: across 30 fresh runs of one build its first path took 61.8 to 163.6 ms, its time following the prime cores' clock over it, and the fastest of each run's nine warm preview repeats spread 23 % (16.87 to 20.77 ms) across ten more fresh runs, steadier than their medians (46 %) but far wider than the under 7 % of the figures the iPhone holds, so only its export and peak memory are held there (the record says why).
  • Size. The release library's size per architecture is measured and reported per release (PD15); Android libraries are 16 KB-aligned (§23).
  • Licences. Every dependency is MIT, Apache-2.0, BSD, ISC, Zlib, Unicode or CC0, or MPL-2.0 used unmodified (UniFFI), as EffectCraft's own rule allows (AGENTS.md, "Clean-room code"); tools/ci.sh checks the list.
  • Observability. The Rust log output goes to os_log on iOS and logcat on Android, at a level the app sets.
  • Accessibility. CraftBridge draws no interface; the samples label every control for VoiceOver and TalkBack.
