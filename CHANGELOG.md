# Changelog

Every artifact (the Rust crates, the Swift package and both Maven artifacts) shares one version. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html), with breaking changes in a major version from 0.1.0 on.

## [Unreleased]

### Added

- `Folders`, in `craftbridge-core` and in the boundary's record, has one more working folder, `staged`, which `prepare` creates and checks as it does the others and which the boundary carries into both bindings: staging copies what it reads of a source from a folder the session may not write beside into it, beside `config` and `models` inside the container, so a project saved with an instance of a bundled template still finds every medium after the system empties the cache and the project is opened again. A copy is named by a SipHash of the bytes it holds, not by where its source sits, so a template an app update installs at a new path is read from the copy it had, and one an update changed is read from a copy of its own while a project saved before the update keeps the media it names. `Folders::working` lists the working folders for whatever else deals with them, and `Folders::inside(container, prefix)` lays every one of them out inside one folder, as a host that runs the engine over one folder does.
- An Android arm64 phone whose processor lacks FP16 is refused when the engine starts: `Engine::start`, `Engine::start_in` and the new `Engine::start_in_with` (which builds the app itself, after the check, and which `start_effects_engine` now uses) answer `Unsupported` in words that name the missing feature (`HWCAP_FPHP` or `HWCAP_ASIMDHP`, read with `getauxval`), before the app is built or a folder is touched, where the arm64 library, built for half-precision arithmetic, would have stopped the app with a signal on a Cortex-A53, A57, A72 or A73. The floor is stated in PD11: Android 10 and later on arm64-v8a with FP16, plus the x86_64 emulator, which has none.
- `rerun` in `craftbridge-process`: it runs one ignored test of the current test binary again in a child started with a changed environment — the helper weighs the child's stdout and stderr itself, and refuses a run whose name matches no test — so a test can meet a variable its own process must not carry while other tests run beside it. xtask's rerunning tests take it from there, and `craftbridge-core`'s tests use it to prove `WGPU_BACKEND=gl` cannot switch the backend the core asks, which only a child started with the variable set can show.
- `craftbridge-core`'s engine GPU lifecycle: `Engine::start` and `Engine::start_in` take the app's `GpuChoice`, ask for that device on the engine thread and hand it to the app before the first call (or the CPU note, which also names a device the app refused), drop the GPU and the preview surface before the next call once the device's failure notice has a report, and answer `suspend_gpu`, which gives the GPU up for the background so no GPU work is submitted, and `resume_gpu`, which asks for a device again and answers the CPU note when none comes; both are exported through the core's boundary as calls that throw `CraftError`.
- An upstream change to EffectCraft's command line now names the adaptations that mirror it: the entries of `tools/adaptations.toml` that follow the command line list the command line's own code they follow — `render`'s flags, queue-and-wait loop and failed-item report (AD3), `render-frame`, its comp reference and its usage line, and where `render` and `bench` hand on their comp as it came (AD4), the whole `--template` handling (AD5), the `bench` functions (AD6), `info`, `commands`, `exec` and `run` (AD10), and `props`, `get` and `set` (AD13) — and plan §15 states the rule that an adaptation mirroring the command line lists the code it mirrors, each place whole code, which xtask's tests check against the pinned source.
- `craftbridge-core`'s preview surface: it configures the app's surface from the core's device (the platform's non-sRGB format, `Fifo` with one frame in flight, and `PostMultiplied` alpha where the surface offers it, else an opaque picture, as on Android), draws a display frame into it aspect-fit between black bars, configures it again on a resize, and answers a `Gpu` error, never a panic, when the surface is outdated or lost or the device refuses a frame.
- `craftbridge-core`'s engine preview calls: `present(params)` draws an app's frame onto the attached surface and shows it — waiting its turn behind a running export as every call does, and answering `Gpu` with the session kept when no surface is attached or the surface is lost or outdated — and `detach_preview` gives the surface up, which the GPU lifecycle also does when it drops the GPU on a failure or a `suspend_gpu`, so an app attaches its surface again once the GPU is back; the native boundary exports both as calls that throw `CraftError`, `attachMetalLayer` attaches the app's `CAMetalLayer` on iOS, and on Android the app's `Surface` comes in as an `ANativeWindow` through the SDK's one JNI call and `attachWindow` attaches it.
- The gate reads Rust with `syn`: `unsafe` and lint attributes are found as the syntax tree holds them (a macro's body too), an unparsable file is reported by name, and `allow(warnings)`, an allowed default clippy group and `rustfmt::skip` on a crate or module fail `rules: lints`; the hand-written source stripper is gone.
- Hardware H.264 and HEVC encoding in `craftbridge-effects`: an `export` that sets `hardware` encodes the movie with the device's VideoToolbox encoder and the platform's AAC encoder, through `craftbridge-media`'s `HardwareEncoder`, `encode_aac` and `Movie`, with the same frame count and size as the software export and every frame within D-12's 40 dB of it; a request that does not set it, another format and a device without the encoder export through EffectCraft's encoders as before. The same encoders run on a Mac, which is how they are tested.
- A `template.render` whose `output` sets `hardware` encodes its movie in hardware as an `export` does: the choice is read from the render request each progress method renders, through one reader, where before only an `export` was read and the render silently encoded in software.
- An `export` or a `template.render` `output` that sets both `queue` and `hardware` is refused before anything renders, as `InvalidParams` naming both fields and saying a queued render encodes through the render queue and its own encoders, where before an `export` dropped the `hardware` and encoded the movie in software without a word, and a template's `output` was refused only for naming `queue`; each field alone behaves as before.
- `craftbridge-core`: an export, render or fill the engine answers `Cancelled` leaves none of the files it listed and wrote, nor the folders it made that then hold nothing, even when the stop lands after its last frame; a listed file it never reached stays as it was, and one that finishes keeps its files. The engine deletes them by the pending-export journal's own rules before it answers, once, for every call that lists outputs; a file the disk will not let go of is answered `Io`, naming it, and stays listed for the next start, as a folder it will not remove does, which holds nothing of the call and leaves the answer `Cancelled`. An export that lists a file a start or a cancel could not delete takes over its entry, so the next start keeps the file that export finishes there, where before it deleted it.

- `craftbridge-core`: `Folders` and `Confinement` — the container and bundle read roots and the container write root an engine starts with, prepared for it — and `CraftError`, the one error every call over the native boundary fails with, with the plan's whole mapping of failures onto it.
- `craftbridge-core`'s engine actor: the `CraftApp` trait an app plugin implements, one engine thread per engine answering its calls in order over oneshot channels, a panic inside any call answered as `Internal` with the session kept serving, and closing or dropping an engine ending its session and joining its thread.
- `craftbridge-media`: `register(on)` puts CraftBridge's decoder factory in FilmCraft's decoder registry and sets the hardware-decoding switch, and `Fallback<D>` wraps a hardware decoder so that, on an error or an in-band parameter change, the stream continues in FilmCraft's software decoder without skipping or repeating a picture, replayed from the last restart sample the oldest picture the caller lacks decodes from (the one before an HEVC CRA until the CRA's own picture is out), however many pictures the failed decoder still held, as far back as the replay bounds reach.
- `craftbridge-media`'s VideoToolbox decoder: on iOS, H.264, HEVC and, where the device decodes it, AV1 (4:2:0, 8-bit and 10-bit) are decoded by the hardware and returned in exactly the frame layout FilmCraft's software decoder produces, wrapped in `Fallback`; where there is no hardware decoder, such as the iOS Simulator, the factory declines and the software decoder takes the stream.
- `craftbridge-media`'s MediaCodec decoder: on Android, H.264, HEVC and, where the device decodes it in hardware, 8-bit AV1 are decoded by the device's hardware decoder, 8-bit pictures through an `AImageReader` of `YUV_420_888` images and, from Android 14 (API 34), 10-bit H.264 and HEVC pictures through P010 hardware buffers (`AHardwareBuffer_lockPlanes`), and returned in exactly the frame layout FilmCraft's software decoder produces, wrapped in `Fallback`; where the device has no hardware decoder for the codec (an emulator's HEVC), or the stream is 10-bit AV1, or 10-bit before Android 14, the factory declines and the software decoder takes the stream, as it does when a 10-bit picture's buffer is not P010 (a vendor-tiled format). The decoder is picked from the device's own codec list (`set_device_codecs`, before `register`), never the platform's default for the type, and a codec counts as hardware by the platform's own answer handed over with the list (`MediaCodecInfo.isHardwareAccelerated`); H.264's SPS and PPS go to the codec as `csd-0` and `csd-1` (HEVC's parameter sets together as `csd-0`, AV1's `av1C` record as `csd-0`), and one codec serves the decoder's life: a seek flushes it with no `start()` after it, and a codec that has output nothing yet is dropped instead.
- `craftbridge-media`'s `Fallback` also switches to the software decoder when the hardware decoder fails while the stream's end is drained, and returns the rest of the stream from it, replayed from a restart sample before the oldest picture the caller does not have yet, so a codec that dies holding pictures loses none of them, where a stream ended early without an error before: a decoder's drain now answers a result, through the new `Draining` trait, since FilmCraft's `VideoDecoder::flush` answers none, and a MediaCodec that fails to drain, or never reaches the end of the stream, is never used again.

- `craftbridge-core`'s export waiting (L3): `CraftApp::request_with_progress` runs an export that reports progress once every `PROGRESS_INTERVAL`, the CLI's 100 ms, and stops when its progress closure answers `false` (an app with no such request keeps the default, which answers `Unsupported`); while `Engine::request_with_progress` runs, every other call waits behind it in the order it was made and `info` is answered from the state the export began with; a `CancelToken` stops the export at its next progress report and the call answers `Cancelled`; a `close` stops the export running and every export waiting, as a cancel does, before joining its thread; and a progress listener that fails is ignored so the export continues.
- `craftbridge-core`'s GPU device: `GpuDevice::request` makes the wgpu device itself — Metal on iOS, Vulkan on Android, the host's on the desktop, GL never — asking `wgpu::Limits::default()` clamped to the adapter, with `max_texture_dimension_2d` capped at 16384 and `max_buffer_size` from the adapter as the compositor takes those two, so a device that offers less than the defaults still answers; it gives `(adapter, device, queue)` for the compositor to render on, and when the app chose `GpuChoice::CpuOnly`, no adapter answered, or the request failed, it answers why in words `info.gpu` can report while every render runs on the CPU.

What the confined session withholds (helpers, scripts) and the model downloads, which would start the system `curl`, answer `Unsupported` on every path, so the session starts no process; any other name `request` is given answers `Unsupported`, naming what was asked and the methods `request` answers.
- `craftbridge-core`'s frame formats: `FrameBytes` and `PixelFormat`, with PNG bytes passed through, straight RGBA kept as it is, and straight RGBA swizzled and premultiplied in place into the BGRA an iOS `CVPixelBuffer` takes, rounded as Apple's own premultiply rounds; a raw buffer whose length is not its size, a side of zero, and a size no buffer can hold are refused as `InvalidParams`, naming the sizes.
- `craftbridge-effects-codegen version`: the engine's version and the full commit of its pin, the constants the plugin's `info` reports as `version` and `pin`, in `rust/effects/craftbridge-effects/src/generated/version.rs`, written by `cargo xtask generate`, which the gate regenerates and compares; so `info`'s `pin` is the commit the workspace builds, in full however `rust/Cargo.toml` spells the pin, and moves with the pin.
- `craftbridge-core`'s `frame` call: `CraftApp::frame` and `Engine::frame` render one frame as PNG, straight RGBA or premultiplied BGRA, answered as `FrameBytes` on the engine thread in the order the calls were made, waiting behind a running export, with `Unsupported` for an app that renders none; and `craftbridge-effects` answers it from a `FrameRequest` (`comp`, `time` or `frame`, `maxSide` or `scale`, `transparent`) resolved as the command line's `render-frame` resolves its flags: its PNG is byte for byte the file `render-frame` writes, and its raw pixels are the ones that file decodes to. A missing comp answers `NotFound` in the command line's words whatever the format, and a request naming both `time` and `frame`, or both `maxSide` and `scale`, which `render-frame`'s usage gives as alternatives, answers `InvalidParams`. `request` still refuses the name `frame`, whose pixels cannot come back through JSON.
- `craftbridge-effects`: the plugin answers `props`, `get`, `set`, `open`, `save`, `saveAs` and `new`. The first three go through the tools the command line's commands of those names call, with a comp or layer given as the command line reads it (an id, a name, `#n`, or `-` for the active comp); the others run `file.open`, `file.save`, `file.saveAs` and `file.newProject`, whose results they answer, inside the folders the confinement allows (the container, and the bundle for reading) and refused by the confinement's own check outside them. `props`'s `depth` is the whole number of group levels the tool expands, as the command line's `mcp` passes it. A file the disk will not read or write — missing, unreadable, unwritable, or a full disk — answers `Io` through these methods, and through `exec` and `run` wherever the engine reports it as a file it cannot read or write.
- `craftbridge-effects`: `export` runs through the core's `request_with_progress`: `RenderRequest` has one field for each flag of the EffectCraft command line's `render`, mapped to the render-queue parameters with the command line's names, defaults and errors; the render runner unqueues the project's other items, queues the request (or renders the project's own queue with `queue`), polls the render at each progress report, stops it on the first `false` and waits for the exporter to remove what it had written, so a cancelled export leaves no output. A parameter `export` does not take, or one of the wrong kind, is refused by its name, as every method refuses its own; an export format the build lacks answers `Unsupported`, under `export` and from any command that refuses one. Any other name `request_with_progress` is given answers `Unsupported`, naming the methods it answers.
- `craftbridge-effects`: `export` lists every file its render may write — each output module's file, every frame of a sequence, every segment and the render log, for each queued item — before the render starts, so a render killed mid-way leaves no partial file once the app starts again and a finished render's files are kept. `renderQueue.render`, the watch folder's two commands, `render.saveCurrentPreview` and `file.exportTimeline`, which have the exporter write a render nothing has listed, answer `Unsupported` through `exec`, `run` and `engine.batch`; a `file.exportTimeline` whose own `prerender` says it renders nothing is no such render and answers as any command.
- `craftbridge-effects`: `template.open` and `template.render` set a template's instance up as the command line's `--template` does — the values checked on a scratch copy before the import, the template imported, the instance wrapped in a composition of its own — and answer the template's missing fonts as `warnings`. `template.render` exports the instance through the render runner, so its files are listed in the pending-export journal like every export's, and the `frame` call renders the instance's frame when its parameters name a `template`. A template whose folder lies outside the container's write root, such as one in the app bundle, is imported from a copy in the container's staged folder, so the media the import writes beside it land inside the container. A request refused for its shape is refused before the template is imported, and a value naming a control the template lacks answers `NotFound`, as a missing control does through any command.
- `craftbridge-effects`: `contentFill.generate` is answered through `request_with_progress`, as `export` is: it lists every frame the fill may write before its background task starts, relays the task's progress at each progress interval and stops the task at the first `false` or on a cancel, so a fill killed mid-way leaves no frame, and no folder it made, once the app starts again, a fill that is stopped or fails leaves none either, and a finished fill's frames are kept. A fill whose folder or frame lies outside the container (in the bundle, relative to the process, or an unsaved project's default in the system's temporary folder) is refused as `Io` in the confinement's words before anything is listed or written, whether or not the engine keeps a journal. `contentFill.generate` and `layer.newContentAwareFill` answer `Unsupported` through `exec`, `run`, `engine.batch`, `replay` and every MCP tool.
- `craftbridge-core`'s pending-export journal: `Engine::start_in(folders, app, gpu)` prepares the folders, deletes each file `pending-exports.json` (in the config folder) still lists that an export killed mid-way wrote, leaves a listed file the export never reached as it was, then removes each folder of a listed file's path that was not there when the file was listed once it holds nothing, clears the journal and reports what it did as `Engine::recovery()`. `CraftApp::request_with_progress` gains `list_outputs`, through which an export lists every file it is about to write before it writes the first (every file of an image sequence included), and the engine clears the list when the export ends whatever its outcome. Entries are stored below the container, so a container that moved is still cleaned; every write is a temporary file renamed into place; only regular files, and empty folders an export made for them, inside the container are ever deleted, never a folder that holds anything, a link or what it points at; a journal whose content is damaged deletes nothing and is replaced, and one the disk will not read when a process takes the journal is set aside unread for a later start (at most 8 at once), never failing the start or an export. A process holds an exclusive lock on `pending-exports.lock` while a start of its own deals with the journal and while its exports run, and writes the journal from what it knows meanwhile, so a journal the disk stops reading mid-run is replaced whole; a start that finds another process holding the lock deletes nothing and a listing that does is refused, each trying again next time, and an idle process holds no lock, which iOS would terminate a suspended app for.
- `craftbridge-effects` (FX-1l): at engine start the EffectCraft app sweeps the engine's folders for every `.effectcraft-<pid>-<n>.tmp` a killed write left — EffectCraft's atomic write, which every file the session's file services write goes through, publishes the file by a rename from exactly such a temporary made beside it, and a hard kill between the create and the rename leaves one behind, a file the pending-export journal can never list because its name is drawn as the write starts (D-17). The sweep matches EffectCraft's own naming rule and a process id no process has now, as the system answers it: the temporary of a process still running, this one or another engine's on the same container such as an app extension's, may be a live write and is kept, and an id the system has given a new process since only keeps its leftover for a later start. It takes only regular files inside the folders of the core's one `Folders::working` list, subfolders included so the media a template import writes deep inside one is swept and a folder added to the list is swept with no second list anywhere, never any other file and never anything outside those folders, following no symbolic link; a file the disk will not give up is tried again at the next start, and the sweep never fails the start.
- `craftbridge-effects`: `replay` runs a JSON-lines repro script through EffectCraft's own replay and answers its report, after checking every line against the confinement and the model-download door so a refused script runs nothing; `timings` answers the command line's `bench` as a document (per-layer and per-effect time, playback frames with and without the layer cache, and with `gpu` the CPU against an attached GPU), at a scale up to Full; `CraftApp::mcp` and `Engine::mcp` answer one line of EffectCraft's MCP transport on the session the methods act on, with the model downloads refused there too. `script` is not a method of the phone build, since a script runs past the confinement: an app that wants what a script does runs the same engine calls in succession through `exec` and `run`, and every command that runs a script is refused in the confinement's words on every path.
- The rest of `tools/update-upstream.sh`: after the pin it names the adaptations of `tools/adaptations.toml` whose upstream items the revision change touched, regenerates the API surface and diffs it (exit 2 on a breaking change), runs the gate, appends the update to `docs/upstream-updates.md`, and names each version of the Android catalog and each Gradle wrapper release that has a newer one; `tools/adaptations.toml` gives each item a table of its own with every file and lines it occupies, a place in the Craft libraries read at the revision its own app builds them at, its ids rise, with each taken once and gaps allowed, and an item's lines that the revision change only moved are named with the lines they moved to. A run on the revision the tree holds changes nothing.
- `craftbridge-process`: the host-only support crate the tools share, with its own kind in the layer table (a tool may depend on it, the core's and the apps' crates only from their tests, and it depends on no CraftBridge crate): `signal_group`, `group_has_live_process` and `stop_group`, which kills a process group and answers once no process of the group is alive and its leader has been reaped, and `Group`, a process started in a process group its guard leads, which ends the whole group when the program that started it ends first, however it ends.
- Platform fonts (FX-3, AD2): at engine start the plugin registers the phone's own font folders with EffectCraft — on iOS the folders CoreText's face list points at, read through a new iOS platform module in `craftbridge-core` (`craftbridge_core::platform`), never a hard-coded `/System/Library/Fonts`; on Android `/system/fonts` — beside the app's `Folders.fonts`. Every app-facing font listing (`text.fonts` through `exec`, `run` steps, the MCP tools that run it — `list_fonts`, `execute_command`, `command_run`, `batch` and each row of `command_batch` — and the `text.fonts` rows of `engine.batch` answers) is trimmed to the faces the phone itself lists, matched by (file, PostScript name), plus the bundled ones, reported with origin `bundled`, with `count` recomputed; every face stays registered, so hidden faces still draw. Where the platform answers no face list the listing passes through unfiltered. The SDK bundles Noto Sans SC and Noto Sans TC Regular region-subset OTFs (SIL OFL 1.1, license and provenance beside them at `rust/effects/craftbridge-effects/assets/fonts/`) so Simplified and Traditional Chinese draw on iOS 26, whose PingFang outlines EffectCraft cannot read.
- `craftbridge-effects`' exporter: an export runs on a thread pool sized from the memory the phone reports available, so a long export cannot outgrow it. `craftbridge-core::available_memory()` reads the figure (`os_proc_available_memory` on iOS, `MemAvailable` from `/proc/meminfo` on Android, nothing on a desktop, in the iOS Simulator or when a phone's figure cannot be read), and the pool has as many threads as half of it holds frames of the export's largest size at 16 bytes a pixel, between one and the machine's cores. With no figure, or memory to spare, an export runs on the threads it already has, so a desktop's exports are unchanged; a smaller pool is kept from one export to the next.
- `craftbridge-effects-ffi`, the one native library an app links: built as `staticlib`, `cdylib` and `lib`, it carries the core's scaffolding and its own, and exports `start_effects_engine(folders, gpu)`, which builds the EffectCraft app for the folders the app names and starts it with `Engine::start_in_with` — so an engine started after an export the system killed deletes that export's partial files and clears its journal before answering, and says what it did through the handle's `recovery`. The app is built behind the engine's own panic guard, `craftbridge_core::engine::guarded`, now public and the one guard the core-ffi's off-thread calls run behind too, so a panic while it is built throws `CraftError`'s `Internal`, as a panic in any engine call does, never an error of UniFFI's own. Library mode generates the call, and the core's types it crosses in, into both languages, the Kotlin under `io.github.christopherlinnett.craftbridge.ffi.effects` beside the core's package.
- `craftbridge-core-ffi` and `rust/uniffi-bindgen`: the core's UniFFI boundary exports `Engine`, `Folders`, `GpuChoice`, `CraftError`, `ProgressListener`, `CancelToken`, `FrameBytes` and `PixelFormat`, and every `Engine` call (`request`, `request_with_progress`, `frame`, `mcp`, `shut_down`) is an `async` call that throws `CraftError`: each reaches the engine as it is first polled and awaits the engine thread's own answer, so calls run in the order they were made and no thread blocks for one; `shut_down` is refused to later calls from the moment it is made (the core's `Engine::begin_close`), and answers at once from inside one of the engine's own calls; `mcp` answers the reply line or `None`, and a closed engine or a caught panic throws `Internal` rather than reading as a reply; `recovery` answers at once with what the start cleaned up after an export the system killed (`Recovery`, with each path as text). A value UniFFI cannot carry is refused with `InvalidParams` by one size check, before it is lowered: a frame of more than `MAX_FRAME_BYTES` (`i32::MAX` less the record's other fields), a `request` or `request_with_progress` answer of more than `MAX_ANSWER_BYTES` (`i32::MAX`) and an `mcp` reply line of more than `MAX_MCP_LINE_BYTES` (`i32::MAX` less its tag and length), since UniFFI's lowering panics beyond `i32::MAX` and Kotlin reads a buffer from one `ByteBuffer` of at most that. Frame bytes are copied as they cross, with no zero-copy promised. In both bindings a `CraftError` variant's text is `detail`, and `uniffi.toml` sets the Kotlin package; `rust/uniffi-bindgen` generates Swift and Kotlin in library mode at the library's UniFFI version, and its test checks every export in both. `craftbridge-core`'s `Engine::send_request`, `send_request_with_progress`, `send_frame` and `send_mcp` hand a call to the engine and answer with its `Answer`, which a caller blocks on or awaits.
- The plug-in door is picked per platform: with a plug-in folder named, Android and the desktop load WebAssembly effect modules from what the confinement lets the engine read, and iOS loads only from a plug-in folder an engine of the app names inside the app's bundle, for as long as that engine lives, judged by where the module's file resolves, answering any other source as a capability the build lacks (`Unsupported`); a folder named outside the bundle admits nothing (plan §19, T24). With no folder named no platform loads plug-ins at all, as before.
- `CraftApp::attach_gpu` and `CraftApp::drop_gpu` hand an app plugin the core's GPU device and take it back, and the EffectCraft plugin drops it on the first fault: `attach_gpu` gives a device to EffectCraft's own compositor and `info.gpu` names it, a `CpuOnly` answer arrives as its reason and renders stay on the CPU, and both of wgpu's failure callbacks — device lost and any uncaptured error — reach the core's failure notice, so the first failure drops the GPU before the next request and `info.gpu` reports the loss in EffectCraft's own words until a new device is attached (plan §16, §17).
- The Android build asks boa for its `jsvalue-enum` value layout, the one that tolerates Android's top-byte-tagged heap pointers, through a target-specific dependency; no other platform's graph carries it, and Android's boa carries no other feature the desktop's lacks (decision D-8).

### Changed

- The gate's mobile stage also lints the libraries' tests on each of the four phone targets, at the levels the host's tests are linted at, so a test that compiles only for a phone (the font tests the simulator and the emulator run) meets the same lints.
- `tools/hooks/pre-push` gates each commit a push carries, checked out into a temporary worktree of its own, instead of the working tree the push comes from: an edit that is not part of the push neither passes nor fails it. Each gated tree gets the plan kit's dependencies from `npm ci`, as `plan/package-lock.json` pins them. A commit whose `tools/ci.sh` is gone or cannot run is refused. A repository's pushes gate one at a time, in one build folder kept warm from push to push.
- `craftbridge-effects-conformance` starts each oracle step in a process group of its own and, when the step outlives its timeout, stops the whole group, so what the step started (a shell script's children, the oracle's helpers) no longer keeps running. When the runner is interrupted or killed while a step runs, the step's group ends with it, since a Ctrl-C at the terminal no longer reaches a step in a group of its own. The pre-push tests take their group signal and their stop from the same crate.
- xtask takes the tree it works on from the run, not from where it was compiled: the folder a `tools/` script names in `CRAFTBRIDGE_ROOT`, for a run that stands inside it, or else the working folder's git top level, checked against the files a CraftBridge tree holds. A run whose tree is not the folder the binary was built in, compared as the file system identifies folders, is refused naming both, with exit 64 (a misused command exits 64 too, so 1 stays a failed check and 2 a breaking API change), so a copy of a tree that kept another tree's build folder can neither read nor write the tree it was copied from.
- A retired adaptation keeps its entry in `tools/adaptations.toml` instead of leaving the list: marked `retired` with the id of the upstream commit whose interface replaced it and holding no items, its id is checked with the others and so is never reused, and a retired entry that keeps items or names no commit id is refused; `tools/update-upstream.sh` lists the retired entries apart from the live ones in its report.
