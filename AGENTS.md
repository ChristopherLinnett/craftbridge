# CraftBridge: rules for agents and contributors

These rules apply to every human and AI contributor and are never broken. `CLAUDE.md` points here. A rule marked **(gate)** is checked by `tools/ci.sh`, which fails when it is broken; the others are checked in review. Each rule exists because of a decision recorded as a GitHub issue labelled `decision`; a rule changes only through such an issue and a pull request that changes this file and its check together. The layout, the layers and the gate are designed in the plan of record, [`plan/EFFECTCRAFT-PLUGIN-PORT-SCOPING.md`](plan/EFFECTCRAFT-PLUGIN-PORT-SCOPING.md) §15; the conventions behind these rules, with their sources, are in [`plan/evidence/07-repository-conventions.md`](plan/evidence/07-repository-conventions.md).

## 1. Layout

- The repository root holds only the files `AGENTS.md`, `CLAUDE.md`, `README.md`, `NOTICE`, `ATTRIBUTION.md`, the two licences, `CHANGELOG.md`, `.gitignore`, `.gitattributes` and `.editorconfig`, the checkout's `.git`, and the folders `rust/`, `ios/`, `android/`, `conformance/`, `docs/`, `tools/`, `plan/` and `.github/`. Nothing that belongs to a platform sits at the root. **(gate)**
- Each platform folder is a complete build of its own: `rust/` (the Cargo workspace), `ios/sdk/` (the Swift package), `android/sdk/` (the Gradle build). `ios/` and `android/` hold only `sdk/` and `samples/`. **(gate)**
- A name that holds nothing git would add — one git ignores, or an empty folder, which git cannot hold — is no part of the repository, so neither rule above counts it.
- Every file is read one way, whichever tool or check reads it: a file the gate reads as text (one it knows by its extension or name, or a script known by its `#!` line) is UTF-8 with no NUL byte; every path is in NFC; a name or extension that spells one the gate knows another way — in ASCII case or in any fold the disk makes (`inner.RS`, `package.swift`, a long s for `s`) — is spelt the canonical way, and a shell script is named `.sh`; no path is a symbolic link; and Rust, Swift, Kotlin and shell sit only in the code folders, bar `plan/plan`, the plan kit's launcher, and the probes a verification ran, kept as they ran under `plan/evidence/`. **(gate)**
- Inside each platform folder the universal core sits beside each app plugin: `rust/core/` beside `rust/<app>/`, `ios/sdk/Sources/CraftBridge` beside `ios/sdk/Sources/CraftBridge<App>`, `android/sdk/core` beside `android/sdk/<app>`. Where a Rust crate's folder sits is gated with its name (§9).
- No `node_modules` folder sits in the code folders: every check skips one as somebody else's packages, while SwiftPM, Gradle and Cargo compile what it holds. **(gate)**
- A library folder holds the library and nothing else. Samples live in `samples/` and consume the library the way an app does: the Swift package by local path, the Gradle build as an included build.
- A platform folder never refers to another platform's code. Every platform reads the shared data in `conformance/`.

## 2. Dependency direction

- The **universal core** knows nothing about any Craft app, not even in its tests. A core crate never depends on an `effectcraft-*` crate or on an app crate; `CraftBridge` and `:core` never import a plugin. The one exception is `craftbridge-media`, which uses FilmCraft's `filmcraft-codecs` and `filmcraft-isobmff`: CraftBridge's decoders register into the decoder registry EffectCraft decodes through (that row's `upstream` in `rust/xtask/src/layers.rs`). **(gate)**
- An **app plugin** depends on the core and on its own Craft app, never on another app's plugin or on a sibling Craft app's code, not even in its tests. Code two plugins need moves into the core. **(gate)**
- Within the core and within a plugin, dependencies point down the layers listed in `rust/xtask/src/layers.rs`. A new crate is added to that table in the same change, as a workspace member in its own folder: a dependency by a path outside the workspace, or on one of the workspace's own crates from anywhere else, is refused, and so is every local package the resolved graph holds, with every feature on, that is no workspace member (brought in by a path, a `[patch]` or a `[replace]`) and every `Cargo.toml` under `rust/` but the workspace's and its members'. A Craft app's crate is known by its name or by the app's repository it comes from. **(gate)**
- `uniffi` appears only in `-ffi` crates. Each app has **one native library**, its `craftbridge-<app>-ffi` crate, the only crate built as a `staticlib` or `cdylib`, and it builds both; no crate is a Rust `dylib`: two Rust libraries in one app collide. **(gate)**
- Host tools (`xtask`, `uniffi-bindgen`, the codegen and conformance crates) may depend on anything; nothing depends on a tool. **(gate)**
- The layer and `uniffi` rules are about what ships, so a dev-dependency, which only a crate's own test build compiles, is outside them; the isolation rules and the tool rule cover it, since a tool may reach every app. **(gate)**

## 3. Never crash

People trust the engine with hours of work. Bad input, a bad call or a full disk produces an error the app can act on, never a crash and never lost work. This outranks feature work.

- **Rust.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!` or `unimplemented!` outside tests. These lints are set once, in `rust/Cargo.toml`; every crate inherits them with `[lints] workspace = true`, and neither the table nor a crate root may weaken them. The five with no exception — `unwrap_used`, `panic`, `todo`, `unimplemented` and `unreachable` — are `forbid`, so the compiler refuses every `allow` of them, however it is spelt; tests keep `unwrap()`, `expect()` and `panic!` through clippy's `allow-*-in-tests` settings in `rust/clippy.toml`, and clippy has no such setting for the other three, so tests do without them. `expect_used` is `deny`. The same calls are named again by path in `rust/clippy.toml` (`disallowed-methods`, `disallowed-macros`, both `deny` in the table), which reach a macro's expansion and a method taken as a value (`.map(Option::unwrap)`), with the other ways to stop the process, `std::process::abort`, `std::panic::panic_any` and `std::panic::resume_unwind`; the tests' clippy run takes those two lints back. Clippy runs in the release profile apps link as well as the dev one. **(gate)** A build script may not weaken them either: a crate has a build script (a `build.rs` Cargo picks up beside its manifest, or one its `package.build` key names) only when its row in `rust/xtask/src/layers.rs` marks it. **(gate)** Nor may code the rules never read: every file a crate's compilation reads, as the compiler's dep-info lists it for each build the gate makes, is one of that crate's own `.rs` files the rules read, so no `#[path]`, `include!`, `include_str!` or `include_bytes!` reaches another file, and every `.rs` file belongs to a crate. **(gate)** The only exception is a provably infallible literal, written as an item-level `#[allow(clippy::expect_used, clippy::disallowed_methods)]` and `.expect("why this cannot fail")`; no other never-crash lint is allowed on an item, and `disallowed_methods` only beside `expect_used`. **(gate)**
- Fail with `Result` and `?`, adding context. Treat every number derived from input as hostile: `get()` instead of indexing, checked or saturating arithmetic, capped allocations, bounded recursion. Handle lock poisoning; treat thread joins as results.
- `panic = "unwind"` stays: the engine thread catches a panic at every call, keeps the document and returns `Internal`. No panic crosses into Swift or Kotlin. **(gate)**
- **Swift.** No force unwrap, `as!`, `try!` or implicitly unwrapped optional (swift-format, and every postfix `!` in `cargo xtask rules`), and no `.unsafelyUnwrapped`, `fatalError`, `precondition`, `preconditionFailure`, `assert`, `assertionFailure`, `exit` or `abort`, called or taken as a value, outside tests. **(gate)** Failures are thrown errors. Test code is what SwiftPM compiles into its test targets, as `swift package describe` lists each target's files: there the banned calls are allowed, and swift-format's three rules still apply except inside a `@Test` function, which swift-format exempts. Tests use Swift Testing: `import XCTest` is refused everywhere, because swift-format exempts a whole file that imports it, and `import Testing` and `@Test` outside a test target. **(gate)** Every file a target compiles lies where the checks read it, never in build output, and every regular target is in a product or used by a test or executable target, so the build compiles it. **(gate)**
- **Kotlin.** No `!!`, `TODO()`, `exitProcess` or `System.exit` in library or sample code. **(gate)** Failures are documented exceptions.
- Every crash fix comes with a test that crashed before the fix.

## 4. Unsafe code

- Hand-written `unsafe` lives only in the crate's own `src/platform/`, in the crates the layer table marks as platform crates, and every block carries a `// SAFETY:` comment. **(gate)**
- `allow(unsafe_code)` appears only crate-wide in an `-ffi` crate (UniFFI's generated scaffolding needs it) and on the `mod platform` declaration in a platform crate's `src/lib.rs`. **(gate)**
- Swift pointer APIs (`Unmanaged`, every `Unsafe…Pointer`, `withUnsafe…`, `OpaquePointer`, `unsafeBitCast`, `unsafeDowncast`) appear only under a `Platform/` folder, in tests as everywhere else. Kotlin `external` (JNI) declarations appear only under a `platform/` folder, in every source set. **(gate)**

## 5. No copy-paste

Never duplicate code by copying it into a second place: not functions, types, widgets, scripts or configuration blocks, and never a "near-identical" variant. Reuse the existing definition; if it almost fits, extend that one definition and repoint every caller; if it lives in a private scope, promote it to one shared definition and consume it everywhere, including the original site. If two pieces only look alike and genuinely cannot share code, say why in the pull request before writing the second one.

- A block of ten lines, or of seventy tokens, repeated anywhere in Rust, Swift, Kotlin or shell fails the gate. Only generated directories and build output are skipped (`plan/` holds none of the four but the plan kit's launcher `plan/plan` and the evidence records' probes, §1), and no file may switch the check off (§10). **(gate)**
- Configuration follows the same rule: every version once (`[workspace.dependencies]`, `gradle/libs.versions.toml`); shared Gradle setup once (`android/sdk/build-logic`); the licence allowlist once (`rust/deny.toml`); the build environment once (`tools/env.sh`).
- Code two Craft app plugins need lives in the universal core, never borrowed from a sibling Craft app.

## 6. Generated code

- Code and data that a generator in this repository writes live only in directories named `generated` or `Generated`, carry an `@generated` header where the format allows comments (every format but those that hold none, such as JSON, CSV and plain text, and binary files), and are written only by `cargo xtask generate`; a marker anywhere else, the root's own files included, is a generated file in the wrong place. **(gate)** Three kinds of written-for-you file are outside this rule: the files a build tool writes for itself (`Cargo.lock`, `Package.resolved`, the Gradle wrapper), which change only through that tool; the `[patch.crates-io]` and `[profile.release]` tables of `rust/Cargo.toml` and the starting `Cargo.lock`, which only `tools/update-upstream.sh` writes, from the pinned EffectCraft (§7); and the plan's views in `plan/`, which the plan kit builds from `plan/EFFECTCRAFT-PLUGIN-PORT-SCOPING.md` and `plan/diagrams/src/` and `plan/plan check --final` checks.
- Generated files are committed and never edited by hand. To change one, change its generator, or for a plan view its source. The gate regenerates everything `cargo xtask generate` writes and fails on any difference, and on any file there git does not track. **(gate)**

## 7. Upstream: EffectCraft

- **EffectCraft is never modified.** CraftBridge builds official `storytold/effectcraft` revisions as they are, never a fork or a patched branch, and opens nothing upstream. The fork `ChristopherLinnett/effectcraft` is only kept in step with upstream.
- What a phone needs EffectCraft to do differently is an **adaptation** in CraftBridge's own crates, written against EffectCraft's public interfaces: it calls EffectCraft, wraps it or follows its behaviour, and never carries a copy of EffectCraft code. Behaviour an adaptation follows from EffectCraft's command line is checked against that command line by the conformance corpus.
- Every adaptation is listed in `tools/adaptations.toml` with the EffectCraft files and items it relies on, no later than the change that adds it, and updated in every change that alters what it relies on, so an update names the adaptations to recheck.
- **Upstream wins.** When EffectCraft gains a public interface that does an adaptation's job, the adaptation moves onto it and leaves the list.
- The pin moves only through `tools/update-upstream.sh`. The `[patch]` tables, the release profile and the starting `Cargo.lock` come from the pinned EffectCraft and are never written by hand.
- One copy of each EffectCraft, FilmCraft and Craft library crate: CraftBridge's decoders register into the same registry EffectCraft decodes through. **(gate)**
- GitHub commands name their account (`GH_TOKEN=$(gh auth token --user ChristopherLinnett) gh …`), because a machine's active login may be another account.

## 8. Licences, assets and brand

- Dependencies use only the licences allowed in `rust/deny.toml`: checked for Cargo by cargo-deny, and for Gradle libraries (what ships and what the tests run with) and SwiftPM packages through `tools/licences.toml`; a Swift package that takes a published package commits its `Package.resolved`, where the packages those take are written. **(gate)** An identifier is added to the allowlist only through a decision issue. MPL-2.0 is allowed only for dependencies used unmodified; JNA is used under Apache-2.0.
- Clean room: no GPL, LGPL or AGPL code; no code, assets or strings copied from another product. Every asset is original or openly licensed and listed in `ATTRIBUTION.md` in the same change.
- CraftBridge is an independent SDK: no ArtCraft name, wordmark or logo in its names, icons, listings or marketing. It says, in plain text, that it is based on EffectCraft by the ArtCraft team.

## 9. Naming

- Rust crates: a core crate is `craftbridge-<area>`, in `rust/core/<name>`; an app plugin's crates and its tools carry the app's noun, `craftbridge-<app>` or `craftbridge-<app>-…`, in `rust/<app>/<name>` (`craftbridge-effects`, later `craftbridge-film`); any other host tool keeps its conventional name (`xtask`, `uniffi-bindgen`), at `rust/<name>`. A crate's folder is its name, spelt exactly, and its library and binary targets carry the crate's name. **(gate)**
- Swift: package `CraftBridge`, modules `CraftBridge`, `CraftBridge<App>` and the generated `CraftBridgeFFI`. Kotlin: packages `io.github.christopherlinnett.craftbridge.<module>`, generated bindings under `io.github.christopherlinnett.craftbridge.ffi.<module>`. Maven: `io.github.christopherlinnett.craftbridge:<module>`.
- Public APIs follow the Rust API Guidelines, the Swift API Design Guidelines, the Kotlin coding conventions and the AndroidX API guidelines ([`plan/evidence/07-repository-conventions.md`](plan/evidence/07-repository-conventions.md)).

## 10. Formatting and lints

- rustfmt (`rust/rustfmt.toml`) and clippy with warnings as errors, for the host and the four mobile targets; `swift format lint --strict` (`ios/sdk/.swift-format`); Spotless with ktlint (`.editorconfig`) and Kotlin warnings as errors, tests included, and Android Lint with warnings as errors, on the debug and the release variant, and Kotlin explicit API mode, on the library code (Kotlin exempts tests from explicit API mode, and Lint runs only its test checks there); shellcheck for every script, told by its `.sh` ending or a `#!` line naming sh, bash, dash or ksh, bar the Gradle wrapper, which Gradle writes, and the duplicate check compares the same scripts. **(gate)**
- The gate's own machinery — `tools/ci.sh`, `tools/env.sh`, `tools/hooks/`, `rust/xtask/`, `rust/.cargo/config.toml`, `android/sdk/settings.gradle.kts`, `android/sdk/gradle.properties`, `android/sdk/build-logic/`, and the single copy of each of `rust/clippy.toml`, `rust/rustfmt.toml`, `rust/deny.toml`, `ios/sdk/.swift-format`, `tools/licences.toml` and the root `.editorconfig` — decides what the gate checks, so it cannot guard itself: a change to any of those files is a gate change, which its pull request names and its review checks for weakened rules. The gate fails on a second copy of any listed configuration file, or of a tool configuration that would act like one, anywhere in the tree: clippy's `clippy.toml` or `.clippy.toml` and rustfmt's `rustfmt.toml` or `.rustfmt.toml` anywhere but their listed paths; cargo-deny's `deny.exceptions.toml` or `.deny.exceptions.toml` (in any folder, `.cargo/` included) is a second `rust/deny.toml`, since it widens the allowlist; any `.editorconfig` but the root's is a second one, since ktlint merges every one up to the root's; and a `rust/.cargo/config` beside `rust/.cargo/config.toml` is a second Cargo configuration, which Cargo reads instead. The gate keeps none of these at all, and fails on any: `.shellcheckrc` or `shellcheckrc` (shellcheck also runs with `--norc`), `.ignore`, a `.gitignore` but the root's and `plan/.gitignore` (jscpd also runs with `--no-gitignore`), and a jscpd ignore marker in the code folders. Gradle reads a `gradle.properties` in a project's own folder as that project's properties, so no other `gradle.properties` sits under `android/sdk` — the build's own is `android/sdk/gradle.properties` alone, and `android/sdk/build-logic`, an included build with properties of its own, is where its own may sit. **(gate)**
- An Android module's `android/sdk/<module>/build.gradle.kts` — one of which every module the settings include has — applies the convention plugin and names its namespace once, and holds only comments, `plugins { id("craftbridge.android.library") }`, `android { namespace = "io.github.christopherlinnett.craftbridge.<module>" }`, and a `dependencies` block whose entries are `api`, `implementation`, `testImplementation` or `androidTestImplementation` of a `project(":…")` or a `libs.<alias>`. The root `android/sdk/build.gradle.kts` holds only comments and a `plugins` block of `alias(libs.plugins.<alias>) apply false` lines and `id("craftbridge.quality")`. The build is written in Kotlin DSL only: Gradle would read a Groovy `build.gradle` or `settings.gradle` in place of the Kotlin file beside it, so those are refused unread. Everything else a build needs is configured once in `android/sdk/build-logic`, which is why a module's own build file never needs to rewire anything: there is no `buildSrc` under `android/sdk`, and no settings file but the build's and `build-logic`'s, since Gradle would run either's scripts outside the convention plugins. **(gate)**
- A lint is never switched off to make a change pass. Fix the code; for a genuine false positive, allow it on the one item, with a comment saying why — never one of §3's never-crash lints, bar `expect_used`'s literal exception. The one check switched off build-wide is Android Lint's `AndroidGradlePluginVersion`, which reports a newer AGP by the day, not by the change; `android/sdk/build-logic` sets it.
- Comments explain why the code is the way it is: an invariant, a constraint, a trade-off. Never issue numbers or history; those belong in the pull request. A guard that looks removable says what it prevents.

## 11. Versions and releases

- One version for every artifact: the Rust crates, the Swift package and both Maven artifacts. It is written only in `rust/Cargo.toml` (`[workspace.package] version`); the release script passes it to Gradle and tags the release with it.
- Semantic versioning: a breaking change is a major version from 0.1.0 on, an addition a minor version, a fix a patch. Tags are `X.Y.Z`. Every user-visible change adds a line to `CHANGELOG.md` under Unreleased in the same pull request.
- Nothing is published without the owner's go-ahead.

## 12. Changes, commits and pull requests

- Every piece of work is a GitHub issue in the CraftBridge project (`https://github.com/users/ChristopherLinnett/projects/9`), with its acceptance and the issues that block it. Work starts only on an issue whose blockers are all done. An issue with sub-issues is never worked directly: it is finished through its sub-issues and closes with the last of them.
- Each issue is built on its own branch, `<task-id>-<slug>` in lower case (`ops-2-doctor`), in its own git worktree outside the checkout (`../craftbridge-worktrees/<branch>`), so every ready issue can proceed at once; the checkout itself stays on `main` or an iteration branch, because git gives a branch to one worktree only. Only two changes to the same files wait for each other, the later one recorded as blocked by the earlier. Once the pull request has merged, the worktree goes with `git worktree remove` and its branch with `git branch -D` (a squash-merged branch is never an ancestor of the iteration branch, so `-d` refuses it once its remote branch is gone), and the remote branch is deleted. The branch merges by pull request into the iteration branch of its wave (`iteration/w0`, `iteration/w1`, …). An iteration branch reaches `main` through one pull request the owner approves. `main` and the iteration branches change only through pull requests, squash-merged once the gate is green. The pull request title and the squash commit are `<TASK-ID>: <summary>` (`OPS-2: Check every build prerequisite with tools/doctor.sh`).
- Closing an issue is what unblocks the issues that depend on it, so an issue is closed when, and only when, its pull request has merged into the iteration branch. GitHub closes issues automatically only on the default branch, so the issue is closed explicitly at that merge; the project's Done status follows the closing, never the other way round. Nothing is marked done that has not merged.
- **The review loop.** A change is built by one side and reviewed by the other: the reviewer reviews the whole change, fixes everything it finds and reports; the builder then reviews the whole change again, the reviewer's fixes included, fixes everything it finds and reports; the same two keep alternating until neither finds anything in the other's work. Only then does the change go up. Every round is a full review with fixes, never a single remark handed back. The pull request records the rounds.
- A question about whether a syntax is legal is settled by the compiler or a syntax-aware analyser, not by argument; a reviewer unsure of a language or tool reads its documentation before claiming a finding.
- Run the gate before pushing (`tools/doctor.sh --install-hooks` makes git run it before every push, for every worktree, on the working tree the push comes from; a push that only deletes branches carries nothing to gate). Report only what ran: say what was tested and what could not be run.
- A decision becomes the issue that carries out its action (labelled `decision`, stating what to do and why), closed by the pull request that does it. Decisions are not written into the repository.
- No agent attribution in commits, pull requests or comments.
- Check, then claim: read the issue and the open pull requests on the same surface before starting, and verify a definition before using it.
