# CraftBridge: rules for agents and contributors

These rules apply to every human and AI contributor and are never broken. `CLAUDE.md` points here. A rule marked **(gate)** is checked by `tools/ci.sh`, which fails when it is broken; the others are checked in review. Each rule exists because of a decision recorded as a GitHub issue labelled `decision`; a rule changes only through such an issue and a pull request that changes this file and its check together. The layout, the layers and the gate are designed in the plan of record, [`plan/EFFECTCRAFT-PLUGIN-PORT-SCOPING.md`](plan/EFFECTCRAFT-PLUGIN-PORT-SCOPING.md) §15; the conventions behind these rules, with their sources, are in [`plan/evidence/07-repository-conventions.md`](plan/evidence/07-repository-conventions.md).

## 1. Layout

- The repository root holds only the files `AGENTS.md`, `CLAUDE.md`, `README.md`, `NOTICE`, `ATTRIBUTION.md`, the two licences, `CHANGELOG.md`, `.gitignore`, `.gitattributes` and `.editorconfig`, the checkout's `.git`, and the folders `rust/`, `ios/`, `android/`, `conformance/`, `docs/`, `tools/`, `plan/` and `.github/`. Nothing that belongs to a platform sits at the root. **(gate)**
- Each platform folder is a complete build of its own: `rust/` (the Cargo workspace), `ios/sdk/` (the Swift package), `android/sdk/` (the Gradle build). `ios/` and `android/` hold only `sdk/` and `samples/`. A toolchain's build files sit only in its own platform folder: no other folder holds a `Cargo.toml`, a `Package.swift`, a `build.gradle(.kts)` or a `settings.gradle(.kts)` — not `conformance/`, `tools/`, `docs/` or `.github/`, not another platform's folder, and not `plan/`, bar the probes kept as they ran under `plan/evidence/` — since a build file there is read by no build and misleads about what is built where. **(gate)**
- A name that holds nothing git would add — one git ignores, or an empty folder, which git cannot hold — is no part of the repository, so neither rule above counts it.
- Every file is read one way, whichever tool or check reads it: a file the gate reads as text (one it knows by its extension or name, or a script known by its `#!` line) is UTF-8 with no NUL byte; every path is in NFC; a name or extension that spells one the gate knows another way — in ASCII case or in any fold the disk makes (`inner.RS`, `package.swift`, a long s for `s`) — is spelt the canonical way, and a shell script is named `.sh`; no path is a symbolic link; and Rust, Swift, Kotlin and shell sit only in the code folders, bar `plan/plan`, the plan kit's launcher, and the probes a verification ran, kept as they ran under `plan/evidence/`; and no hand-written Java sits under `android/sdk`, because every check that guards the SDK's Kotlin — §3's bans, §4's JNI confinement and §9's packages — reads Kotlin's own syntax tree and would see none of it. **(gate)**
- No file git tracks holds an absolute home-folder path, `/Users/<name>/` or `/home/<name>/`, in any case and however a tool prints it: glued to a compiler's option (`-L/home/<name>`), through macOS's firmlink (`/System/Volumes/Data/Users/<name>`), under `/var/home` or `/usr/home`, or with JSON's escaped slashes. The repository is public, and such a path names the user of the machine that wrote it, so a capture, a log or a state file writes the home folder `$HOME`; `/Users/Shared`, the folder macOS gives every user, names nobody. `git grep` reads the work tree's copy of every tracked file, binary ones too; a file git does not track, or ignores, is no part of what the repository publishes. **(gate)**
- Inside each platform folder the universal core sits beside each app plugin: `rust/core/` beside `rust/<app>/`, `ios/sdk/Sources/CraftBridge` beside `ios/sdk/Sources/CraftBridge<App>`, `android/sdk/core` beside `android/sdk/<app>`. Where a Rust crate's folder sits is gated with its name (§9). A regular Swift target sits at `ios/sdk/Sources/<name>`, where `swift package describe` finds it: one moved elsewhere by `path:`, or found in another folder SwiftPM searches (`Source/`, `src/`, `srcs/`), is refused, since the layout places it. **(gate)**
- No `node_modules` folder sits in the code folders: every check skips one as somebody else's packages, while SwiftPM, Gradle and Cargo compile what it holds. **(gate)**
- A library folder holds the library and nothing else. Samples live in `samples/` and consume the library the way an app does: the Swift package by local path, the Gradle build as an included build.
- A platform folder never refers to another platform's code. Every platform reads the shared data in `conformance/`.

## 2. Dependency direction

- The **universal core** knows nothing about any Craft app, not even in its tests. A core crate never depends on an `effectcraft-*` crate or on an app crate; `CraftBridge` and `:core` never import a plugin. The one exception is `craftbridge-media`, which uses FilmCraft's `filmcraft-codecs`, `filmcraft-color`, `filmcraft-frame` and `filmcraft-isobmff`: CraftBridge's decoders register into the decoder registry EffectCraft decodes through (that row's `upstream` in `rust/xtask/src/layers.rs`). **(gate)**
- An **app plugin** depends on the core and on its own Craft app, never on another app's plugin or on a sibling Craft app's code, not even in its tests. Code two plugins need moves into the core. **(gate)**
- Within the core and within a plugin, dependencies point down the layers listed in `rust/xtask/src/layers.rs`. A new crate is added to that table in the same change, as a workspace member in its own folder: a dependency by a path outside the workspace, or on one of the workspace's own crates from anywhere else, is refused, and so is every local package the resolved graph holds, with every feature on, that is no workspace member (brought in by a path, a `[patch]` or a `[replace]`), the gate's lint library's own graph included, which holds no local package but the library, and every `Cargo.toml` under `rust/` but the workspace's, its members' and the gate's lint library's, `rust/never-crash-lints/Cargo.toml`, which `cargo dylint` builds in the stages that run it (§3, §10). The workspace's default members, as Cargo resolves `default-members` in `rust/Cargo.toml`, are exactly the crates the table says ship — the core's, the app plugins' and a combined distribution crate, never a host tool or the support crate — since the phone-target lint runs read a crate in full, its tests and every feature, only when it is a default member, and not at all when no default member takes it, as none takes a combined distribution crate. A Craft app's crate is known by its name or by the app's repository it comes from. **(gate)**
- `uniffi` appears only in `-ffi` crates. Each app has **one native library**, its distribution library, the only kind of crate an app links built as a `staticlib` or `cdylib`, and it builds both; no crate is a Rust `dylib`: two Rust libraries in one app collide. An app that ships one plugin links that plugin's `craftbridge-<app>-ffi`; one that ships several plugins together links their **combined distribution crate**, `craftbridge-<bundle>-ffi` (`craftbridge-all-ffi`), in place of any plugin's `-ffi`, never beside one. A combined distribution crate takes the crates of two app plugins or more, as Rust libraries, may take the core's, and takes no Craft app's own crate but through that app's plugin, not even in its tests; nothing but a host tool depends on it, not even a crate's tests, so no other library carries it. A crate's kind and name in `rust/xtask/src/layers.rs` say which crate is a distribution library, and nothing else marks one. Every build takes the SDK's from the table — its one app's own, or with several apps their combined distribution crate: xtask builds the bindings and the XCFramework from it, and `tools/build-android.sh` builds the one `cargo xtask sdk-library` names. The one name Cargo needs, the dev-dependency in `rust/uniffi-bindgen`'s manifest through which the bindgen's tests find the library, is held to the table by xtask's tests. The gate's lint library is a `cdylib` too, but dylint's driver loads it and no app links it. **(gate)**
- Host tools (`xtask`, `uniffi-bindgen`, the codegen and conformance crates) may depend on anything; nothing depends on a tool. **(gate)**
- A **host-only support crate** (`craftbridge-process`: starting a process in a group of its own and stopping the whole group, and running one ignored test of the current test binary again in a child started with a changed environment) holds code the tools share, once. A tool may depend on it; the core's crates, the apps' and a combined distribution crate only from their tests, since nothing they ship may carry host code; and it depends on no CraftBridge crate and no Craft app's crate, even in its own tests. **(gate)**
- The layer and `uniffi` rules are about what ships, so a dev-dependency, which only a crate's own test build compiles, is outside them, and a combined distribution crate's plugins are counted from what it ships; the isolation rules, the tool rule, the rule that nothing but a tool depends on a combined distribution crate, and the support crate's rule cover it, since a tool may reach every app, a combined distribution crate links every app it ships, and a support crate takes no CraftBridge crate. **(gate)**

## 3. Never crash

People trust the engine with hours of work. Bad input, a bad call or a full disk produces an error the app can act on, never a crash and never lost work. This outranks feature work.

- **Rust.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!` or `unimplemented!` outside tests, no `std::process::exit`, and no index into a slice, a string, a map or any other collection outside tests. These lints are set once, in `rust/Cargo.toml`; every crate inherits them with `[lints] workspace = true`, and neither the table nor a crate root may weaken them. Every crate inherits the workspace edition the same way, with `edition.workspace = true`, and none of its targets (`[lib]`, `[[bin]]`, a test, an example or a bench) sets one of its own: what the compiler accepts, and which lints exist to apply, change between editions, so a crate or target pinning an edition for itself compiles under rules no other crate follows. The ones with no item-level exception — `unwrap_used`, `panic`, `todo`, `unimplemented`, `unreachable`, `exit` (which refuses `std::process::exit`, what the Swift and Kotlin rules below refuse in those languages), and `indexing_slicing` and `string_slice` (which refuse an index into a slice, array or vector and into a string, since an index panics on a hostile number: the `get()` rule below, enforced) — are `forbid`, so the compiler refuses every `allow` of them, however it is spelt; tests (a `#[test]` function or `#[cfg(test)]` code, which is what clippy reads as a test, in any target) keep `unwrap()`, `expect()`, `panic!` and indexing through clippy's `allow-*-in-tests` settings in `rust/clippy.toml`, and clippy has no such setting for `todo`, `unimplemented`, `unreachable`, `exit` or `string_slice`, so tests do without those. `expect_used` is `deny`. The same calls are named again by path in `rust/clippy.toml` (`disallowed-methods`, `disallowed-macros`, both `deny` in the table), which reach a macro's expansion and a method taken as a value (`.map(Option::unwrap)`), with the other ways to stop the process — `std::process::exit` again, since clippy's `exit` passes every method and any function called `main`; `std::process::abort`; the C library's `libc::exit`, `libc::_exit` and `libc::abort`; `std::panic::panic_any` and `std::panic::resume_unwind` — and with indexing's own trait methods, `core::ops::Index::index` and `core::ops::IndexMut::index_mut`, so an index spelled as a call (`d.index(i)`, `(Index::index)(d, i)`, a captured `C::index`) falls to the same rule whatever it indexes, and with `std::env::args` and `std::env::vars`, which panic on an argument or a variable that is not Unicode, so code reads `args_os` and `vars_os` and reports such an item. The tests' clippy run takes those two lints back. Clippy runs in the release profile apps link as well as the dev one. **(gate)** A `[]` clippy's index lints do not read — on a map, a `VecDeque` or anything with an `Index` of its own, which clippy reads only when it is held by value and its `get` returns what the index yields — is refused by `collection_indexing`, a `forbid` lint of the gate's lint library `rust/never-crash-lints` (§10), since only the type checker knows what a `[]` indexes, wherever the workspace writes it, a macro of the crate or of another workspace crate included (reported at the macro's call), but not inside a macro of std or a dependency, whose expansion nobody here can edit; inside another workspace crate's macro, where clippy's index lints read nothing, it refuses a slice's, array's, vector's and string's `[]` too: `cargo dylint`, at the release `tools/env.sh` pins, builds the library with the nightly its own `rust-toolchain.toml` pins and checks with it the shipping targets clippy's first run lints and the library builds of the phone runs; it compiles no test target, so tests keep their `[]`; `cargo test -p xtask` runs it over a probe crate, so a library that compiles and lints nothing fails the `rust_test` stage, and runs it and clippy over one probe, so each index is reported once, by one or the other, never by both and never by neither. The gate also runs clippy over the library's own code, on that nightly and failing on any warning, in the same two runs as over the workspace (what it ships, then its tests with the two calls-by-path lints taken back), under the levels the workspace's lint table sets, and the library's own lint over what it ships: Cargo shares a workspace's tables only within it, so the library's manifest carries the lint table and the edition and licence of `[workspace.package]` as its own workspace's, never the release version, and its crate inherits them as a member does; a test of `cargo test -p xtask` fails while a copy and its original differ, and every rule that reads a member's manifest or graph reads the library's too — its lint and edition inheritance, its build script, its local dependencies and what its compilation reads. Every other stage builds the workspace with its own toolchain, and the workspace table sets no level for the library's lints, which would outrank the library's own. **(gate)** A build script may not weaken them either: a crate has a build script (a `build.rs` Cargo picks up beside its manifest, or one its `package.build` key names) only when its row in `rust/xtask/src/layers.rs` marks it. **(gate)** Nor may code the rules never read: every file a crate's compilation reads, as the compiler's dep-info lists it for each build the gate makes, is one of that crate's own `.rs` files the rules read (or, for the lint library's runs, the library they load, built from `rust/never-crash-lints`), so no `#[path]`, `include!`, `include_str!` or `include_bytes!` reaches another file, and every `.rs` file belongs to a crate. **(gate)** The only exception is a provably infallible literal, written as an item-level `#[allow(clippy::expect_used, clippy::disallowed_methods)]` and `.expect("why this cannot fail")`, outside the tokens of a macro call, where the macro decides what an attribute lands on (§10); no other never-crash lint is allowed on an item, and `disallowed_methods` only beside `expect_used`. **(gate)**
- Fail with `Result` and `?`, adding context. Treat every number derived from input as hostile: `get()` instead of indexing, on a map, a `VecDeque` or any other collection as well, whose `[]` panics on a missing key or index — outside tests the lint library's `collection_indexing` refuses it, above; checked or saturating arithmetic, capped allocations, bounded recursion. Handle lock poisoning; treat thread joins as results.
- `panic = "unwind"` stays: the engine thread catches a panic at every call, keeps the document and returns `Internal`. No panic crosses into Swift or Kotlin. **(gate)**
- **Swift.** No force unwrap, `as!`, `try!` or implicitly unwrapped optional (swift-format, and every postfix `!` in `cargo xtask swift-lint`, which reads Swift through the compiler's language server with the settings of every build of the package that ships — Debug and Release for each Apple slice the native library is built for, as `rust/rust-toolchain.toml` lists them (the iOS device and the iOS Simulator) — so each `#if` branch a shipping build compiles is read resolved), and no `.unsafelyUnwrapped`, `fatalError`, `precondition`, `preconditionFailure`, `assert`, `assertionFailure`, `exit` or `abort`, called or taken as a value, outside tests. **(gate)** The one other exception is UniFFI's generated Swift, in `ios/sdk/Sources/CraftBridgeFFI/Platform/Generated/` alone: its templates are fixed, so the Swift stages exempt that folder from the rules they cannot meet — `try!`, force unwraps and `fatalError` among them — each named once, with its reason, where its stage keeps its rules (`rust/xtask/src/swift_format.rs`, `rust/xtask/src/swift_lint.rs`); every other rule, §4's pointer rule included, holds there, and every rule holds on all other Swift, generated or written. **(gate)** Failures are thrown errors. Test code is what SwiftPM compiles into its test targets, as `swift package describe` lists each target's files: there the banned calls are allowed, and swift-format's three rules still apply except inside a `@Test` function, which swift-format exempts. Tests use Swift Testing: `import XCTest` is refused everywhere, because swift-format exempts a whole file that imports it, and `import Testing` and `@Test` outside a test target. **(gate)** Every file a target compiles lies where the checks read it, never in build output, and every regular target is in a product or used by a test or executable target, so the build compiles it. **(gate)**
- **Kotlin.** No `!!`, `TODO()`, `exitProcess` or `System.exit` in library or sample code. **(gate)** Failures are documented exceptions. Nor may Kotlin sit where no compilation reads it: every Kotlin or Java file under a module's `src` lies in a source folder of one of the compilations AGP builds for the module, as its variant API lists them, so none is formatted and never compiled — not in `src/testRelease/kotlin`, which AGP 9 compiles for no library, a misspelt folder, or among the resources. **(gate)**
- Every crash fix comes with a test that crashed before the fix.

## 4. Unsafe code

- Hand-written `unsafe` lives only in the crate's own `src/platform/`, in the crates the layer table marks as platform crates, and every block carries a `// SAFETY:` comment; outside them the keyword appears only in the one attribute the next bullet names, on the lint library's two dylint exports, and nowhere else. **(gate)**
- `allow(unsafe_code)` appears only crate-wide in an `-ffi` crate (UniFFI's generated scaffolding needs it), on the `mod platform` declaration in a platform crate's `src/lib.rs`, and on the two dylint entry-point exports of the gate's lint library (§10): dylint loads a library by the names of its entry points, which edition 2024 makes their crate spell `#[unsafe(no_mangle)]`, with the keyword; that attribute on those two exports, and its allowance, are the keyword's only use in the library, and no `unsafe` block sits there. **(gate)**
- Swift pointer APIs (`Unmanaged`, every `Unsafe…Pointer`, `withUnsafe…`, `OpaquePointer`, `unsafeBitCast`, `unsafeDowncast`), a pointer type named through a type alias, and a binding of a declaration to a C symbol (`@_silgen_name`, `@_cdecl`, `@c`, `@_extern`) appear only under a `Platform/` folder, in tests as everywhere else. Kotlin `external` (JNI) declarations appear only under a `platform/` folder, in every source set. **(gate)**

## 5. No copy-paste

Never duplicate code by copying it into a second place: not functions, types, widgets, scripts or configuration blocks, and never a "near-identical" variant. Reuse the existing definition; if it almost fits, extend that one definition and repoint every caller; if it lives in a private scope, promote it to one shared definition and consume it everywhere, including the original site. If two pieces only look alike and genuinely cannot share code, say why in the pull request before writing the second one.

- A block of ten lines, or of seventy tokens, repeated anywhere in Rust, Swift, Kotlin or shell fails the gate. Only generated directories and build output are skipped (`plan/` holds none of the four but the plan kit's launcher `plan/plan` and the evidence records' probes, §1), and no file may switch the check off (§10). **(gate)**
- Configuration follows the same rule: every version once (`[workspace.dependencies]`, `gradle/libs.versions.toml`); shared Gradle setup once (`android/sdk/build-logic`); the licence allowlist once (`rust/deny.toml`); the build environment once (`tools/env.sh`).
- Code two Craft app plugins need lives in the universal core, never borrowed from a sibling Craft app.

## 6. Generated code

- Code and data that a generator in this repository writes live only in directories named `generated` or `Generated`, carry an `@generated` header where the format allows comments (every format but those that hold none, such as JSON, CSV and plain text, and binary files), and are written only by `cargo xtask generate`; a marker anywhere else, the root's own files included, is a generated file in the wrong place. **(gate)** Three kinds of written-for-you file are outside this rule: the files a build tool writes for itself (`Cargo.lock`, `Package.resolved`, the Gradle wrapper), which change only through that tool; the `[patch.crates-io]`, `[profile.dev]` and `[profile.release]` tables of `rust/Cargo.toml` and the starting `Cargo.lock`, which only `tools/update-upstream.sh` writes, from the pinned EffectCraft (§7); and the plan's views in `plan/`, which the plan kit builds from `plan/EFFECTCRAFT-PLUGIN-PORT-SCOPING.md` and `plan/diagrams/src/`: the gate rebuilds those views from their sources and fails on any byte that differs, bar the drawing in each diagram's SVG export, which only draw.io Desktop writes, and `plan/plan check --final` checks the plan against its own writing rules and reports a view older than what builds it. **(gate)**
- Generated files are committed and never edited by hand. To change one, change its generator, or for a plan view its source. The gate regenerates everything `cargo xtask generate` writes and fails on any difference, and on any file there git does not track, and it rebuilds the plan's views from their sources the same way and fails on any byte that differs, and on a diagram export no source builds. **(gate)**

## 7. Upstream: EffectCraft

- **EffectCraft is never modified.** CraftBridge builds official `storytold/effectcraft` revisions as they are, never a fork or a patched branch, and opens nothing upstream. The fork `ChristopherLinnett/effectcraft` is only kept in step with upstream.
- What a phone needs EffectCraft to do differently is an **adaptation** in CraftBridge's own crates, written against EffectCraft's public interfaces: it calls EffectCraft, wraps it or follows its behaviour, and never carries a copy of EffectCraft code. Behaviour an adaptation follows from EffectCraft's command line is checked against that command line by the conformance corpus.
- Every adaptation is listed in `tools/adaptations.toml` with the EffectCraft files and items it relies on, no later than the change that adds it, and updated in every change that alters what it relies on, so an update names the adaptations to recheck.
- **Upstream wins.** When EffectCraft gains a public interface that does an adaptation's job, the adaptation moves onto it and is **retired** in the list, not deleted: its entry stays in `tools/adaptations.toml`, marked `retired` with the id of the upstream commit whose interface replaced it and with its items removed, so its id is never used again. The reader checks a retired entry's id with the others, and that it names that commit and holds no items, and reads nothing else of it; the update loop's report lists retired entries apart from the live ones.
- The pin moves only through `tools/update-upstream.sh`, and only to an official revision: a commit official `storytold/effectcraft` main reaches, named by its id, never a branch, a tag or a pull request's head. The `[patch]` tables, the dev and release profiles (the dev one optimises EffectCraft's and FilmCraft's pixel and codec crates, so the tests run them as EffectCraft's own tests do, while CraftBridge's own crates keep their debug assertions and overflow checks, which the gate holds every build of tests to in every unit of theirs it compiles — the tests, the libraries they link, and the build scripts and proc-macros that make what they run — from Cargo's own report of the profile it built each unit in) and the starting `Cargo.lock` come from the pinned EffectCraft and are never written by hand; every EffectCraft, FilmCraft and Craft library package in `rust/Cargo.lock` comes from a source the pin sanctions, down to the commit Cargo builds; and no Cargo configuration Cargo reads for a build in `rust/` — the repository's own, those in every folder above the checkout, the cargo home's, whatever those `include`, and the environment the gate runs in — holds a `[patch]`, `paths` or a `[source]` replacement, any of which would build another copy around the pin. Nor do they, or the environment, hold a switch that changes what the gate's Rust tools check — rustflags or rustdocflags, a compiler, a compiler wrapper, rustdoc or rustfmt, a test runner, a linker, a dependency's build-script override or any other key of a target table, a profile, an alias, the build target, another lockfile than the committed one, an `[env]` entry, an unlock of nightly configuration, another clippy configuration, or a dylint variable, which names the lint library's driver, the libraries it loads and the flags and configuration its lints read — and the gate runs only the toolchain `rust/rust-toolchain.toml` pins, and in the lint library's folder only the nightly `rust/never-crash-lints/rust-toolchain.toml` pins: a `RUSTUP_TOOLCHAIN` or a `+toolchain` argument naming another toolchain, and any rustup override of `rust/` or of the library's folder, is refused, while the variable rustup hands every command it starts under the pin is the pin, naming it, and no pin in the library's folder, whose commands run without it. Every cargo a tool's own binary starts — xtask's, from `env!("CARGO")`, which rustup did not start and so carries no variable, and the one the bindgen starts for itself to ask about the library's crates — names that pin in that variable, read from `rust/rust-toolchain.toml`'s one definition (`rust/xtask/src/pin.rs`), because cargo runs each crate outside the workspace's folder, which every registry crate is, with its compiler in that crate's own folder, where rustup reads that folder's toolchain file, so no crate's own file ever decides which toolchain builds CraftBridge; a command a tool starts in the lint library's folder alone starts without the variable, as every command there does, so rustup reads the nightly that folder pins, and `cargo dylint`, started in `rust/` like the rest, takes that nightly from the library's folder itself. Each switch is named once, in `tools/refused-switches.tsv`, by its configuration key and the variables Cargo reads it from; the gate refuses each, naming the variable, or the file and the key, and the repository's own configuration may set only its `xtask` alias, while that runs the xtask package. **(gate)**
- One copy of each EffectCraft, FilmCraft and Craft library crate: CraftBridge's decoders register into the same registry EffectCraft decodes through. The one second copy allowed is a Craft library crate the pinned EffectCraft's own lock already resolves at two official revisions, exactly as that lock has it. **(gate)**
- GitHub commands name their account (`GH_TOKEN=$(gh auth token --user ChristopherLinnett) gh …`), because a machine's active login may be another account.

## 8. Licences, assets and brand

- Dependencies use only the licences allowed in `rust/deny.toml`: checked for Cargo by cargo-deny, and for Gradle libraries (what ships, what the tests run with, and the detekt the gate runs its Kotlin checks with, its own rules' tests included) and SwiftPM packages through `tools/licences.toml`; a Swift package that takes a published package commits its `Package.resolved`, where the packages those take are written. **(gate)** An identifier is added to the allowlist only through a decision issue. MPL-2.0 is allowed only for dependencies used unmodified; JNA is used under Apache-2.0.
- Clean room: no GPL, LGPL or AGPL code; no code, assets or strings copied from another product. Every asset is original or openly licensed and listed in `ATTRIBUTION.md` in the same change.
- CraftBridge is an independent SDK: no ArtCraft name, wordmark or logo in its names, icons, listings or marketing. It says, in plain text, that it is based on EffectCraft by the ArtCraft team.

## 9. Naming

- Rust crates: a core crate is `craftbridge-<area>`, in `rust/core/<name>`; an app plugin's crates and its tools carry the app's noun, `craftbridge-<app>` or `craftbridge-<app>-…`, in `rust/<app>/<name>` (`craftbridge-effects`, later `craftbridge-film`); any other host tool keeps its conventional name (`xtask`, `uniffi-bindgen`), at `rust/<name>`; a host-only support crate is `craftbridge-<job>` at `rust/<name>` and, like a core crate, names no app; a combined distribution crate is `craftbridge-<bundle>-ffi` at `rust/<name>` and names no app either, since it ships several (`craftbridge-all-ffi`). A core crate's name carries none of the Craft apps' nouns as a segment, in any case and between `-` or `_`, which Cargo reads alike: `craftbridge-film-utils` and `craftbridge-film_utils` are refused, because the core serves every app and a name that names one mislabels the shelf it sits on. A crate's folder is its name, spelt exactly, and its library and binary targets carry the crate's name. **(gate)**
- Swift: package `CraftBridge`, modules `CraftBridge`, `CraftBridge<App>` and the generated `CraftBridgeFFI`. Kotlin: packages `io.github.christopherlinnett.craftbridge.<module>`, generated bindings under `io.github.christopherlinnett.craftbridge.ffi.<module>` **(gate)**. Maven: `io.github.christopherlinnett.craftbridge:<module>`.
- Public APIs follow the Rust API Guidelines, the Swift API Design Guidelines, the Kotlin coding conventions and the AndroidX API guidelines ([`plan/evidence/07-repository-conventions.md`](plan/evidence/07-repository-conventions.md)).
- A public call written by hand never takes the name of a public call that the generated facade declares on the same type — a command namespace's word on the engine, a command's name on a namespace's type, and in Swift a type the facade nests: a call that belongs to a namespace is an extension of the namespace's generated type under a name the namespace does not give (`engine.templates.open(…)`), and a call whose name a namespace or one of its commands has takes another (plan §22, §23). Neither compiler refuses every form, and a call that clashes reaches whichever the compiler ranks first. Swift refuses only a second member of the same whole name, so a method with arguments would stand beside a property, or a method with other labels, of that name; the `swift_build` stage compares the base name of every public member, read with its file from the compiler's own symbol graphs of each build the package ships. Kotlin refuses only a member property beside an extension property of its name, which it reads as shadowing it, so a function of that name, or an extension with other parameters beside a command, compiles; detekt's `GeneratedNameTaken` compares the name of every public member and extension, reading a call's type, and the calls declared on it, from the compiler's own analysis, and what is generated from the module's generated folder. **(gate)**

## 10. Formatting and lints

- rustfmt (`rust/rustfmt.toml`) and clippy with warnings as errors, for the host and the four mobile targets; `swift format lint --strict` (`ios/sdk/.swift-format`) and SwiftLint's `missing_docs` (`ios/sdk/.swiftlint.yml`), which also reads `open` declarations, protocol requirements and enum cases, bar the rules UniFFI's generated Swift is exempt from (§3); Spotless with ktlint (`.editorconfig`) and Kotlin warnings as errors, tests included, and Android Lint with warnings as errors, on the debug and the release variant, and Kotlin explicit API mode, on the library code (Kotlin exempts tests from explicit API mode, and Lint runs only its test checks there), bar UniFFI's generated Kotlin bindings (`io/github/christopherlinnett/craftbridge/ffi/<module>/` of a module's `src/generated/kotlin`), whose files suppress the two errors the mode reports on the helpers UniFFI writes with no visibility; detekt (`android/sdk/build-logic/detekt-rules/profiles/`), which reads Kotlin with its types resolved, on every variant and test component of each module: §3's bans on what ships; on all written code, tests included, §4's JNI rule, §9's rule for the names the generated facade gives, the refusal of a `@Test` TestNG never runs (whose JVM method returns a value, or which `@Ignore`, `enabled = false` or an `invocationCount` below one switches off, under its own `@Test` or the one over its class that makes a test of every public method there — a test never run says nothing in any report, not even a skip, so its rule goes unchecked while the run reads green), and the refusal of a suppression written over a whole file, switching a detekt rule off on an item, or of a compiler error, as the compiler's own analysis names one; and §9's packages, the generated bindings' too; shellcheck for every script, told by its `.sh` ending or a `#!` line naming sh, bash, dash or ksh, bar the Gradle wrapper, which Gradle writes, and the duplicate check compares the same scripts. **(gate)**
- The gate's own machinery — `tools/ci.sh`, `tools/env.sh`, `tools/refused-switches.tsv`, `tools/oracle.sh`, `tools/ios-device-test.sh`, `tools/device-tests.tsv`, `tools/build-xcframework.sh`, `tools/build-android.sh`, `.github/workflows/ci.yml`, `rust/xtask/`, `rust/never-crash-lints/`, `rust/effects/craftbridge-effects-conformance/`, `rust/craftbridge-process/`, `rust/.cargo/config.toml`, `android/sdk/settings.gradle.kts`, `android/sdk/gradle.properties`, `android/sdk/build-logic/`, and the single copy of each of `rust/clippy.toml`, `rust/rustfmt.toml`, `rust/deny.toml`, `rust/rust-toolchain.toml`, `android/sdk/gradle/libs.versions.toml`, `ios/sdk/.swift-format`, `ios/sdk/.swiftlint.yml`, `tools/licences.toml` and the root `.editorconfig` — decides what the gate checks, so it cannot guard itself: a change to any of those files is a gate change, which its pull request names and its review checks for weakened rules. The gate fails on a second copy of any listed configuration file, or of a tool configuration that would act like one, anywhere in the tree: clippy's `clippy.toml` or `.clippy.toml` and rustfmt's `rustfmt.toml` or `.rustfmt.toml` anywhere but their listed paths; cargo-deny's `deny.exceptions.toml` or `.deny.exceptions.toml` (in any folder, `.cargo/` included) is a second `rust/deny.toml`, since it widens the allowlist; rustup reads the toolchain pin `rust-toolchain.toml` — or the older `rust-toolchain` — from the folder a command runs in and above, so a second copy switches which clippy and rustfmt the gate gets, bar the lint library's own pin `rust/never-crash-lints/rust-toolchain.toml`, read only in that folder, which holds no workspace code; every Gradle version sits once in the build's catalog `android/sdk/gradle/libs.versions.toml`, since it pins the ktlint and Spotless the Kotlin checks run on, and a second `libs.versions.toml` is a second source of those versions even in `build-logic`; any `.editorconfig` but the root's is a second one, since ktlint merges every one up to the root's; and a `rust/.cargo/config` beside `rust/.cargo/config.toml` is a second Cargo configuration, which Cargo reads instead. The gate keeps none of these at all, and fails on any: `.shellcheckrc` or `shellcheckrc` (shellcheck also runs with `--norc`), `.ignore`, a `.gitignore` but the root's and `plan/.gitignore` (jscpd also runs with `--no-gitignore`), a jscpd ignore marker in the code folders, and a `.sourcekit-lsp` folder, whose configuration SourceKit-LSP merges over the options the Swift stage starts it with. Gradle reads a `gradle.properties` in a project's own folder as that project's properties, so no other `gradle.properties` sits under `android/sdk` — the build's own is `android/sdk/gradle.properties` alone, and `android/sdk/build-logic`, an included build with properties of its own, is where its own may sit. **(gate)**
- The gate reads each language through that language's own tooling, never through a text scanner of its own: Rust with `syn` (the `unsafe` rule of §4 and the lint-attribute rule of §3, which find `unsafe` and every attribute as the syntax tree holds them, an attribute name spelt as a raw identifier as the attribute the compiler reads, and in a macro's body too, where an attribute on whatever item the macro's caller hands it, or one written in the tokens a macro call hands a macro (which may take them apart and put them together elsewhere), is read as on a module, and one whose level or whole text the macro fills in, or makes of a `#` and brackets it is given apart, as any level, and report a file `syn` cannot parse, or one nested deeper than it reads; the lint-attribute rule also refuses `allow`, `expect` or `warn` of any default clippy group or of `warnings` wherever it sits, and `rustfmt::skip` on a crate root or a module, `cfg_attr(test, …)` aside), Swift through SwiftLint and the compiler's language server, Kotlin through detekt. The Gradle build files below are no Kotlin read at all: their grammar allows one comment form, a whole line starting with `//`, and refuses every other line it does not list, so no comment or string syntax is ever scanned. **(gate)**
- An Android module's `android/sdk/<module>/build.gradle.kts` — one of which every module the settings include has — applies the convention plugin and names its namespace once, and holds only comments, `plugins { id("craftbridge.android.library") }`, `android { namespace = "io.github.christopherlinnett.craftbridge.<module>" }`, and a `dependencies` block whose entries are `api`, `implementation`, `testImplementation` or `androidTestImplementation` of a `project(":…")` or a `libs.<alias>`. The root `android/sdk/build.gradle.kts` holds only comments and a `plugins` block of `alias(libs.plugins.<alias>) apply false` lines and `id("craftbridge.quality")`. The build is written in Kotlin DSL only: Gradle would read a Groovy `build.gradle` or `settings.gradle` in place of the Kotlin file beside it, so those are refused unread. Everything else a build needs is configured once in `android/sdk/build-logic`, which is why a module's own build file never needs to rewire anything: there is no `buildSrc` under `android/sdk`, and no settings file but the build's and `build-logic`'s, since Gradle would run either's scripts outside the convention plugins. **(gate)**
- A lint is never switched off to make a change pass. Fix the code; for a genuine false positive, allow it on the one item, with a comment saying why — never one of §3's never-crash lints, bar `expect_used`'s literal exception. The checks switched off build-wide are Android Lint's `AndroidGradlePluginVersion` and `GradleDependency`, which report a newer AGP, Gradle or library by the day, not by the change. Newer releases are looked for in the upstream update loop instead (`tools/update-upstream.sh`, plan §24), which names each version in `gradle/libs.versions.toml` and the Gradle wrapper that has one, and each is taken in a change of its own where it is written (§5 keeps every version there once); `android/sdk/build-logic` sets the switch-off.
- Comments explain why the code is the way it is: an invariant, a constraint, a trade-off. Never issue numbers or history; those belong in the pull request. A guard that looks removable says what it prevents.

## 11. Versions and releases

- One version for every artifact: the Rust crates, the Swift package and both Maven artifacts. It is written only in `rust/Cargo.toml` (`[workspace.package] version`); the release script passes it to Gradle and tags the release with it.
- Semantic versioning: a breaking change is a major version from 0.1.0 on, an addition a minor version, a fix a patch. Tags are `X.Y.Z`. Every user-visible change adds a line to `CHANGELOG.md` under Unreleased in the same pull request.
- Nothing is published without the owner's go-ahead.

## 12. Changes, commits and pull requests

- Every piece of work is a GitHub issue in the CraftBridge project (`https://github.com/users/ChristopherLinnett/projects/9`), with its acceptance and the issues that block it. Work starts only on an issue whose blockers are all done. An issue with sub-issues is never worked directly: it is finished through its sub-issues and closes with the last of them.
- Each issue is built on its own branch, `<task-id>-<slug>` in lower case (`ops-2-doctor`), cut from `origin/main` straight after a fetch, in its own git worktree outside the checkout (`../craftbridge-worktrees/<branch>`), so every ready issue can proceed at once; the checkout itself stays on `main`, because git gives a branch to one worktree only. Only two changes to the same files wait for each other, the later one recorded as blocked by the earlier. `main` changes only through pull requests: the branch's pull request is squash-merged into `main` as soon as its review loop is clean and the checks for what it touches pass, with no approval and no hosted check to wait for, so every new change starts from the same point; a wave is the order of work on the board, never a branch. Once the pull request has merged, the worktree goes with `git worktree remove` and its branch with `git branch -D` (a squash-merged branch is never an ancestor of `main`, so `-d` refuses it once its remote branch is gone), and the remote branch is deleted. The pull request title and the squash commit are `<TASK-ID>: <summary>` (`OPS-2: Check every build prerequisite with tools/doctor.sh`).
- Closing an issue is what unblocks the issues that depend on it, so an issue is closed when, and only when, its pull request has merged into `main`: the pull request's description gives each issue it finishes a closing keyword of its own (`Closes #12, closes #13`), and GitHub, which reads those keywords only in a pull request into its default branch, `main`, closes each issue so named at the merge; the project's Done status follows the closing, never the other way round. Nothing is marked done that has not merged.
- **The review loop.** A change is built by one side and reviewed by the other: the reviewer reviews the whole change, fixes everything it finds and reports; the builder then reviews the whole change again, the reviewer's fixes included, fixes everything it finds and reports; the same two keep alternating until neither finds anything in the other's work. Only then does the change go up. Every round is a full review with fixes, never a single remark handed back. The pull request records the rounds.
- A question about whether a syntax is legal is settled by the compiler or a syntax-aware analyser, not by argument; a reviewer unsure of a language or tool reads its documentation before claiming a finding.
- **Hosted CI on `main` is the full gate.** `.github/workflows/ci.yml` runs `tools/ci.sh` on GitHub-hosted runners for every pull request to `main` and every push to it, every stage of it in at least one of its jobs, each job taking its stages from `tools/ci.sh --hosted`, where every stage the Linux job leaves to macOS gives its reason: the gate refuses to start while one gives none, or while a stage is in neither job. Locally a change runs only the checks for what it touches — `tools/ci.sh` with the stages that read the files it changes, `rules` and `duplicates` always, and `cargo test -p` for each crate it changes and each crate that calls what it changed — and never the full gate, before a push or after a merge. A merge waits for nothing hosted: a hosted failure on `main` is fixed on a branch of its own when it fires. No git hook gates a push: the checks a change needs follow from what it changes, which the paths a push carries cannot tell — the crates that call what changed, a platform branch inside a shared file, a change to the gate's own machinery, whose stages are the whole gate — so a hook would either run close to the full gate or pass a push on checks it skipped. Report only what ran: say what was tested and what could not be run.
- A decision becomes the issue that carries out its action (labelled `decision`, stating what to do and why), closed by the pull request that does it. Decisions are not written into the repository.
- No agent attribution in commits, pull requests or comments.
- Check, then claim: read the issue and the open pull requests on the same surface before starting, and verify a definition before using it.
