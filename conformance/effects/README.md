# EffectCraft conformance corpus

The scenarios (T1–T24 of the plan, §28) that every platform will run against the EffectCraft command line, which is the oracle, together with their fixtures (`fixtures/`) and the running example's template recipe, `birthday-card.jsonl`, which `tools/birthday-card.sh` replays with the oracle into the template every sample bundles. The data here belongs to no platform: the desktop runner (`rust/effects/craftbridge-effects-conformance`), the Swift tests (`ios/sdk/Tests`, which run the plug-in's side of each scenario on the iPhone simulator) and the Android instrumented tests (`android/sdk/effects/src/androidTest`, which run it on the Android emulator, the build packing this folder into the test APK as it is) all read it, so a scenario is written once. Each of the three refuses a key or a kind it does not read, so a key, a kind or a comparison the corpus gains is read by all three (`corpus.rs`, `Corpus.swift`, `Corpus.kt`) in the same change. T1 to T22 and T24 are here, T22 on the plug-in alone, since the command line stops a render only by being killed. T22 is deterministic only on the desktop, where the runner holds the export until the stop reaches it. On a device it is bounded: the SDKs cannot hold an export, so it renders on while the stop made at the engine's beat is on its way, and the stop is judged by the render queue's record (`UserStopped`), so a device that renders the export before the stop arrives reports a race, and never passes.

`corpus.toml` holds the scenarios, and its header says how one is written: steps (one oracle invocation each, and the calls that make the same step on the plug-in) and what is checked after them, on the oracle and on the plug-in, whose output and files a comparison holds against the oracle's. The desktop runner starts each side as a process in one cleared environment that holds only its own configuration folder, so nothing in the shell running it, such as fonts in `HOME`, thread counts or GPU switches, changes what either renders. It compares what the two produce with each other and with what the corpus says they must, and for an encoded export applies D-12: the same frame count and size, and every decoded frame within 40 dB PSNR. A frame the GPU renders is held to the compositor's own tolerance against the CPU's. A PNG sequence is held to the same files byte for byte, a GIF to the same decoded frames pixel for pixel, and a cancelled export to no file left behind.

The oracle is the official EffectCraft command line at the pinned revision, built by `tools/oracle.sh`. The gate's `conformance` stage builds it and runs the runner; by hand:

```sh
tools/ci.sh conformance
# or
(cd rust && cargo run -p craftbridge-effects-conformance -- --oracle "$(../tools/oracle.sh)" --scenario T5)
```

`baseline.toml` is not part of the corpus: it is the per-device baseline of the running example (plan §9, §29, V5). It defines what the Swift real-app test (`RealAppBaselineTests`) and the Kotlin instrumented check (`BaselineOnDevice`) measure, the names of their figures (the costs a release is flagged on, on every platform but those a figure's `unheld_on` names, and the conditions each run was made under) and the one line each prints, how a release is compared with the record, and it holds the record of those figures on each acceptance phone, which the release script reads. The Swift tests check that a record is complete (`BaselineTests`). The measurement is only a baseline when it ran alone, in an app of its own, on a quiet phone, so the Swift test runs only on the device runner or where `CRAFTBRIDGE_BASELINE=1` in its environment asks for it (`TEST_RUNNER_CRAFTBRIDGE_BASELINE=1` through `xcodebuild test`), and never beside the gate's other suites.
